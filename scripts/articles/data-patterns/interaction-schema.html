Pending interactions are the paused moments of an agent conversation: a form waiting to be filled, a confirmation waiting for a click. They are short-lived, stateful and security-sensitive, which makes their schema worth getting right.

The document

Why JSON Schema

Storing a real JSON Schema means the same definition drives three things: client rendering (many form libraries render JSON Schema directly), server validation on submit (with a validator such as jsonschema) and the capability's own parameter schema, from which it is usually derived. One definition, no drift.

Keep display concerns (titles, labels, order) in a separate ui object so the schema stays a pure validation contract.

Revision and fingerprint

  • revision increments whenever the server changes the form. Submissions must carry the current revision.
  • fingerprint hashes the capability id and the arguments the user will be confirming. It guarantees that what was confirmed is what gets executed (see human-in-the-loop).

One open interaction per conversation

Enforce it with a partial unique index:

{ conversation_id: 1 }  unique, partialFilterExpression: { status: "open" }
{ status: 1, expires_at: 1 }                     — expiry sweeper
{ tenant_id: 1, created_at: -1 }                 — admin views

Creating a new interaction first marks any open one as superseded within the same logical operation. The partial unique index guarantees you never end up with two open forms competing for the same conversation.

Resolution record

When an interaction closes, set resolved_at and a resolution object: who resolved it, the submitted values (or a redacted form of them), and the resulting turn id. Do not delete the document straight away. Resolved interactions answer support questions like "did I actually confirm that?" Keep them for a few weeks with a TTL on resolved_at.
