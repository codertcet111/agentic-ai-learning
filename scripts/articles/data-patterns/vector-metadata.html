Vectors are only half of a retrieval system. The other half is metadata: where a chunk came from, who may see it, which version of the document it belongs to, and which model embedded it. Whether your vectors live in MongoDB Atlas Vector Search, pgvector, OpenSearch or a dedicated vector database, the metadata deserves a proper schema.

The chunk document

{
  "_id": "chk_hr-leave-policy_v7_0012",
  "tenant_id": "acme",
  "collection": "hr_policies",
  "document_id": "doc_hr-leave-policy",
  "document_version": 7,
  "content_hash": "sha256:41c…",
  "source_uri": "https://intranet.example.com/policies/leave",
  "title": "Annual Leave Policy",
  "section_path": ["4. Carry-over", "4.2 Limits"],
  "page": 6,
  "text": "Employees may carry over up to five days …",
  "token_count": 214,
  "acl": {"countries": ["UK"], "roles": ["employee", "manager"]},
  "language": "en",
  "embedding_model": "text-embed-v3",
  "embedding_dim": 1024,
  "indexed_at": ISODate("…"),
  "active": true
}

Same store or separate?

  • Same store (for example MongoDB Atlas Vector Search, or Postgres with pgvector): the embedding sits on the same document, and metadata filters run inside the vector query. This is the simplest option, with no sync problem.
  • Separate vector store: keep the chunk document in MongoDB as the source of truth and copy the filterable fields (tenant, collection, ACL, active, language) into the vector store's metadata. A re-index job keeps them in sync.

Either way, the fields you filter on at query time must be available inside the vector search, not applied afterwards.

ACL in metadata, decision in the domain

The acl field lets retrieval pre-filter cheaply. The principal's attributes (country, roles) come from the session, which the domain API confirmed at login. The orchestrator never decides on its own that a user is a manager. It reads that from the domain and passes it into the filter.

Versioning

When a document changes, write new chunks with the next document_version, then flip active on the old ones to false in one step. Queries filter on active: true. This avoids a window where half-old, half-new chunks are served, and lets you roll back by flipping the flag back.

Embedding model per chunk

Store the model id and dimension on every chunk. When you change embedding models, vectors from the old and new models are not comparable. Build the new index alongside the old one, switch queries over once it is complete, then delete the old vectors. Without the field, you cannot tell which chunks still need re-embedding.

Useful indexes

{ document_id: 1, document_version: 1 }
{ content_hash: 1 }                                  — skip unchanged chunks on re-index
{ tenant_id: 1, collection: 1, active: 1 }
