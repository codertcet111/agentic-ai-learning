Atomic upserts

Increment counters at the end of each turn with one upsert. No read-modify-write and no locks:

db.usage_daily.update_one(
    {"_id": f"{tenant}:{day}"},
    {"$inc": {
        "turns": 1,
        "llm_calls": calls,
        "input_tokens": tin,
        "output_tokens": tout,
        "cost_usd_estimate": cost,
        f"by_model.{model}.calls": calls,
        f"by_capability.{cap_key}": 1,
     },
     "$setOnInsert": {"tenant_id": tenant, "day": day},
     "$set": {"updated_at": now}},
    upsert=True)

Capability ids contain dots, which MongoDB interprets as path separators. Encode them (for example replace . with __) before using them as field names.

Per-principal counters for quotas

Daily tenant totals suit dashboards. Quotas need finer granularity: per principal per day, checked during turn admission. Store those in a separate collection with a TTL of a few days. For per-minute rate limits, use Redis (see step 17).

Estimates are not invoices

The cost figure is an estimate computed from your configured prices. Prices change, cached tokens are billed differently, retries add calls you may not count, and providers round differently. Use the counters for trends and limits. For billing customers, reconcile against the provider's usage exports every month, and keep the price table versioned so you can explain historical figures.

What to chart

  • Tokens per turn over time. A step change means a prompt or catalog got bigger.
  • LLM calls per turn. Rising values mean more replanning.
  • Share of large-model calls. This checks your model routing.
  • Top capabilities by tenant. This shows what users actually do with the assistant.
