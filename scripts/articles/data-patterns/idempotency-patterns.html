Networks fail in the worst possible place: after the server did the work and before the client heard about it. The client retries. Without idempotency, the user gets two messages, two leave requests or two refunds. With it, the retry returns the first result.

Three layers of protection

LayerKeyProtects against
Message appendClient idempotency_keyDuplicate user messages from retries or offline queues
Turn admissionClient client_request_idRunning the graph twice for one request
Upstream writeServer operation_idExecuting a domain write twice

Each layer catches cases the others miss, so use all three.

Client keys

The client generates a UUID when the user presses Send and reuses it for every retry of that message. It must be generated once per user action, not once per HTTP attempt. Mobile apps that queue messages offline store the key with the queued message.

Partial unique indexes

db.messages.createIndex(
  {conversation_id: 1, idempotency_key: 1},
  {unique: true,
   partialFilterExpression: {idempotency_key: {$type: "string"}}})

The partial filter means messages without a key (system or assistant messages) are not checked for uniqueness. On a duplicate-key error, read the existing document and return it with a normal 200 response. The client should not be able to tell a replay from the original.

Replay the result, not just the acceptance

For turns, it is not enough to reject the duplicate. The client needs the answer. Store result_message_id on the ledger entry when the turn completes. A replayed request then:

  • finds a completed entry → returns that assistant message,
  • finds a running entry → returns 409 turn_in_progress so the client polls,
  • finds a failed entry → returns the same error, so the user can choose to resend with a new key.

Operation ids for writes

Upstream writes use an operation_id built by the server from turn_id and step index, for example trn_88:step_3. Send it as an Idempotency-Key header. This protects against the orchestrator's own retries, and against a crash between invoking a write and recording that it happened. If the upstream API does not support idempotency keys, ask the owning team to add it before you expose that write to an agent. It is the most valuable change they can make for you.

Expiry

Idempotency records do not need to live forever. Twenty-four hours covers realistic retry windows. Messages keep their key for the life of the message, which is harmless. Upstream idempotency stores usually expire keys after a day or so, and that is fine.
