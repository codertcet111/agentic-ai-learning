Chat looks like the simplest data in an AI product. It is also the data you will query in more ways than you expect: rendering the UI, building LLM context, support investigations, analytics, deletion requests. This article gives a schema that serves all of them.

The message document

{
  "_id": ObjectId("…"),
  "conversation_id": "cnv_19b2",
  "tenant_id": "acme",
  "sequence": 42,
  "role": "assistant",
  "turn_id": "trn_88",
  "agent_id": "hr_assistant",
  "locale": "en",
  "content": {
    "text": "Your request for 6–7 November has been submitted.",
    "blocks": [{"type": "card", "title": "Leave request #5531", "status": "pending"}]
  },
  "tool_calls": [
    {"id": "tc_1", "capability": "leave.request.create",
     "status": "ok", "step_result_id": "sr_904"}
  ],
  "usage": {"input_tokens": 3120, "output_tokens": 210, "llm_calls": 3},
  "created_at": ISODate("2026-10-29T10:41:07Z"),
  "redacted": false
}

Field choices explained

  • tenant_id on every message. It is redundant with the conversation, but it means every query and every index can be scoped by tenant without a join, and a missing tenant filter is easy to spot in review.
  • sequence, not created_at, for ordering. Server clocks differ; sequences do not.
  • content.text and content.blocks. Text is always present for accessibility, notifications and LLM context. Blocks are optional rich UI.
  • tool_calls with step_result_id. Auditors can see exactly what the assistant did and follow the link to the full result, without bloating the message.
  • usage per assistant message. Cheap to record, very useful for cost questions by conversation.

Indexes

{ conversation_id: 1, sequence: 1 }            unique   — render and context window
{ conversation_id: 1, idempotency_key: 1 }     unique, partial — safe retries
{ tenant_id: 1, created_at: -1 }                         — admin views, retention jobs
{ "tool_calls.capability": 1, created_at: -1 }           — "who used this tool?"

Add the last one only if you actually run that query. Multikey indexes on arrays are useful but not free.

Common queries

// Render the latest 50 messages
db.messages.find({conversation_id: cid}).sort({sequence: -1}).limit(50)

// Incremental sync from the client
db.messages.find({conversation_id: cid, sequence: {$gt: lastSeen}}).sort({sequence: 1})

// Context window for turn N (everything before it)
db.messages.find({conversation_id: cid, sequence: {$lt: turnStartSeq}})
           .sort({sequence: -1}).limit(20)

Redaction and deletion

For a user's deletion request, a background job sets content to a placeholder, empties tool-call arguments and sets redacted: true, keeping ids and sequence so other messages stay consistent. Deleting documents outright leaves gaps in sequences, which breaks clients that expect continuity. Coordinate with legal on which approach your obligations require.
