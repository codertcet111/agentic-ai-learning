Most agentic systems that fail in production do not fail because the model is weak. They fail because nobody drew a line between the part of the system that talks and the part that decides. Business rules leak into prompts, permission checks live in graph state, and six months later the "AI service" has quietly become a second copy of the product's backend, written in English.

The first step of this series is therefore not code. It is a boundary.

Two planes, two jobs

Split the system into two planes with different owners and different failure modes.

  • The domain plane is the system of record. It owns data, authorization, validation and every write. Payroll rules, leave balances, inventory counts and refund limits live here. It already exists in most companies as a set of REST or RPC services.
  • The orchestration plane owns the conversation. It stores chat history, decides which tool to call next, fills in arguments, asks clarifying questions and turns structured results into natural language. It never owns a business fact.

The orchestrator talks to the domain through a narrow invoke contract: a typed request naming a capability and its arguments, and a typed envelope coming back with either a result or a structured error. The orchestrator forwards the same user credentials the web app would use, so the domain applies exactly the same permissions.

The test for where a rule belongs

If a rule must hold even when the model is offline, misbehaving, or replaced by a different model, it belongs in the domain plane, not in a prompt.

"Employees cannot approve their own expense claims" is a domain rule. If it lives only in a system prompt, a cleverly phrased message will eventually get around it. If it lives in the expense API, the model can ask as many times as it likes and the API will refuse each time.

"Ask for the date range before searching leave history" is an orchestration rule. Breaking it produces a worse conversation, not a security incident. It is fine for that to live in planner policy.

A worked example

Imagine an HR copilot that can answer "how many leave days do I have left?" and "book Friday off".

User ──► Chat UI ──► Orchestrator ──► HR API  (GET /leave/balance)
                         │       └──► HR API  (POST /leave/requests)
                         ├── Mongo: messages, turns, pending forms
                         └── LLM: plan → resolve args → compose reply

The orchestrator never computes a leave balance. It calls the balance endpoint and phrases the answer. It never decides whether Friday can be booked; it collects the date, shows a confirmation form, and lets the HR API accept or reject the request. If the API returns 409 overlapping_request, the orchestrator explains that politely. It does not try to work around it.

What goes wrong without the boundary

  • Duplicated logic drifts. The web app changes the carry-over policy; the prompt still describes the old one; the bot gives wrong answers with full confidence.
  • Permissions become probabilistic. A check that runs only because the model chose to run it is not a check.
  • Testing gets expensive. When rules hide in prompts, the only way to test them is to call a real model many times and hope.
  • Audits get hard. "Why was this approved?" should be answered by a domain log, not by replaying a conversation.

A one-page boundary document

Before writing the first graph node, write a short document listing:

  1. The three to ten domain APIs the agent will call, with their auth model.
  2. Which of them are read-only and which mutate data.
  3. Any rule that currently exists only in someone's head or in UI code. Move these into the API first.
  4. What the orchestrator is allowed to store (messages, form state, usage counters) and what it must never store (tokens, raw domain records beyond what the user saw).

This document becomes the reference for code review. When someone opens a pull request adding a business rule to a prompt, the conversation is short: "that belongs in the API."

Where this leads

Every later step in this series assumes the boundary exists. Layering (step 2) keeps imports pointing one way. Request context (step 3) carries credentials across the boundary without storing them. The capability catalog (step 9) is the published shape of the domain plane. Once the line is drawn, the rest of the architecture has somewhere to stand.
