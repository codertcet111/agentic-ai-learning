Real workflows need input in the middle. "Which manager should approve this?" "Confirm you want to cancel order #4412." A chat agent that handles these by just reading the next free-text message will eventually merge two unrelated intents. Pending interactions make the pause explicit.

The model

When a graph node needs structured input, it does not ask a question in plain text and hope. It creates a pending interaction:

{
  "_id": "pi_…",
  "conversation_id": "cnv_…",
  "turn_id": "trn_…",
  "kind": "form",                      // form | confirmation | choice
  "revision": 1,
  "status": "open",                    // open | submitted | superseded | expired
  "schema": {
    "type": "object",
    "required": ["start_date", "end_date"],
    "properties": {
      "start_date": {"type": "string", "format": "date"},
      "end_date":   {"type": "string", "format": "date"},
      "note":       {"type": "string", "maxLength": 200}
    }
  },
  "prefill": {"start_date": "2026-11-06"},
  "expires_at": "…",
  "resume_node": "submit_leave_request"
}

The assistant message carries a block referencing pi_…, and the client renders a real form. The graph run ends, and the checkpoint records where to resume.

Resuming: only by form submission

The client resumes with a dedicated control message, not a chat message:

POST /conversations/cnv_…/turns
{
  "type": "form_submission",
  "pending_interaction_id": "pi_…",
  "revision": 1,
  "values": {"start_date": "2026-11-06", "end_date": "2026-11-07"}
}

The server checks that the interaction is open, that the revision matches, and that the values validate against the stored schema. Only then does it load the checkpoint and continue at resume_node.

Free text supersedes

Users ignore forms all the time. They type "actually, never mind, what's my balance?" while a leave form is open. That message must not be fed into the paused workflow. Instead:

  1. Mark the open interaction superseded.
  2. Discard its checkpoint.
  3. Run the new message as a fresh turn.

The client greys out the old form. If the user later wants it back, they ask again and get a new interaction with fresh prefill.

Revisions and stale UI

Sometimes the server changes a form while it is open, for example by narrowing date options after a policy check. Increment revision and send the update. A submission carrying the old revision is rejected with the new form attached, so a stale browser tab cannot submit values the server no longer accepts.

Expiry

Open interactions should not live forever. Set expires_at to something reasonable (an hour for confirmations, a day for longer forms). When one expires, append a short assistant message saying so. Silent expiry confuses users who come back the next morning and click Submit.

Test this flow: open form → user sends free text → old form becomes superseded → new turn answers the free text → submitting the old form returns a clear error. Users do exactly this in production.
