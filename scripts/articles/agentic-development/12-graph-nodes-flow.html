Step 11 built the skeleton. This step walks through what each node does in a production pipeline and, just as important, what each one must not do.

load_session → route_request ─┬─► direct recipe ─────────────────────► compose
                               └─► plan_next_step ─┬─► resolve_arguments → invoke_capability ─┐
                                        ▲          ├─► request_input (pause)                  │
                                        │          └─► compose_response                       │
                                        └──────────── evaluate_condition ◄────────────────────┘

load_session

Hydrates what the turn needs: the session's pinned catalog filtered to this principal, the active agent definition (persona, policy, allowed capabilities), locale and the transcript window. No LLM calls. If the session has expired, it short-circuits to a fixed "please sign in again" response.

route_request

Decides between a direct recipe (an exact known command, step 15) and the model path. In multi-agent setups it also picks which sub-agent owns the turn. A small, cheap model or plain rules usually suffice here.

plan_next_step

The core LLM decision. Given the user's message, the transcript window, the filtered capability cards and any results so far, it returns one of:

  • call_tool with a capability id and the user's intent in its own words,
  • need_input with what is missing,
  • answer when it has enough to reply.

The output is a typed schema (step 13), never free text.

resolve_arguments

Turns intent into concrete arguments that validate against the capability's schema. Dates like "next Friday" become ISO dates in the user's timezone. Entity names that need ids trigger lookups whose results are appended to lookup_trace, followed by a replan (step 14). The resolver never silently picks the first search result.

invoke_capability

Checks that the capability is in the session's allowed set, checks explicit_action for writes, calls the provider (step 10), stores the full result in step_results and puts a compact summary and the result id in state.

evaluate_condition

Some workflows branch on results: "if the balance is under 3 days, warn before creating the request". Prefer deterministic code over the result's fields. Use a small LLM call with a typed boolean output only when the condition is genuinely fuzzy.

request_input

Creates a pending interaction (step 8) with a schema and prefill, adds a short message explaining what is needed, and ends the run. The checkpoint holds the resume point.

compose_response

Produces what the user reads. It receives structured results and the plan, not raw tool payloads, and writes text in the user's locale with fallbacks (step 16). It sets response_finalized so no later node composes again.

Typical turn sequences

User saysNode sequence
"How many leave days do I have?"load → route → plan → resolve → invoke → plan → compose
"Book Friday off"load → route → plan → resolve → ask (form)
(submits form)resume → invoke → plan → compose
"reset conversation"load → route → recipe → compose

Record these sequences for your golden cases and keep them in the repository. When a refactor changes one, the diff tells you exactly which behaviour moved. The Langfuse span tree (see the lab) shows the same sequence for any real turn.
