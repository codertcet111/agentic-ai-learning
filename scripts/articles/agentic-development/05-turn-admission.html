A turn is one user message handled end to end: admission, graph run, persisted reply. In a demo, turns arrive one at a time. In production they arrive twice (double-tap on mobile), out of order (flaky network), or in parallel (two tabs). Turn admission is the gate that keeps the transcript consistent anyway.

The three guarantees

  1. At most one turn runs per conversation at a time.
  2. A retried request with the same client id gets the original result, not a second run.
  3. A request based on an outdated view of the conversation is rejected clearly.

The fence: compare-and-set on revision

The client sends the conversation revision it last saw. Admission advances it atomically only if it still matches and no turn is active:

res = conversations.find_one_and_update(
    {"_id": cid, "revision": expected_rev,
     "status": "active", "active_turn_id": None},
    {"$set": {"active_turn_id": turn_id, "updated_at": now},
     "$inc": {"revision": 1}},
    return_document=ReturnDocument.AFTER,
)
if res is None:
    raise RevisionConflict(cid)

Because MongoDB applies the filter and update as one atomic operation on a single document, two concurrent requests cannot both win. The loser gets None and a conflict error.

The turn ledger

A separate turn_ledger collection records each turn's lifecycle:

{
  "_id": "trn_…",
  "conversation_id": "cnv_…",
  "client_request_id": "c-8f2…",
  "status": "running",          // pending → running → completed | failed | cancelled
  "run_id": "…",
  "started_at": "…",
  "finished_at": null,
  "result_message_id": null
}

A unique index on (conversation_id, client_request_id) makes retries safe. Before checking the revision, look up the ledger by client request id. If a completed entry exists, return its stored result. If a running one exists, tell the client to wait or poll.

Replay by client request id before rejecting on revision. Otherwise a mobile client that retries after a timeout gets a conflict for a turn that actually succeeded.

Where Redis fits

A Redis lease (SET turn:cnv_… NX PX 30000) is a fast way to bounce obvious duplicates before touching Mongo. It is useful, but it is advisory. If Redis is down or a lease expires early, the Mongo fence still decides. Never design a flow where Redis being unavailable lets two turns run.

Releasing the fence

When the graph finishes, in a single update: mark the ledger entry completed, link the assistant message, and clear active_turn_id. On failure, mark it failed and clear the fence too. A turn that crashes without cleanup is handled by a sweeper that clears fences older than your maximum turn duration and marks those ledger entries failed with reason abandoned.

Client contract

  • 200 with the assistant message: success, or a replay of an earlier success.
  • 409 revision_conflict with the current revision: refresh the transcript and let the user resend.
  • 409 turn_in_progress: show a spinner and poll.
  • 410 conversation_closed: start a new thread.

Spell these out in your API docs. Front-end developers handle conflicts well when the server tells them precisely what happened.
