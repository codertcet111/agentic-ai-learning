With the orchestration boundary drawn, the next question is how to organise the orchestrator itself. A pattern that holds up well is four layers with strictly one-directional imports.

API routes      → transport: HTTP, auth headers, request ids, response envelopes
Services        → use cases: admit a turn, append messages, run the graph
Agents / graph  → behaviour: plan, resolve arguments, invoke tools, compose
Providers       → outbound: HTTP to domain APIs, LLM gateway, retrieval

Persistence and cache sit beside Services, never inside graph nodes.

What each layer is allowed to know

API routes

Routes parse the request, pull credentials and locale into a request context, call one service method and map the result to an HTTP response. They contain no prompt text and no Mongo queries. A route should be short enough to read in one glance.

Application services

Services coordinate a use case. "Handle a chat message" means: check the conversation is active, acquire the turn fence, append the user message, run the graph, persist the assistant message, release the fence. Services know about repositories and the graph runner, but not about HTTP frameworks.

Agents and the graph

Graph nodes decide what to do next. They read graph state, call the LLM through a gateway interface, and call capabilities through a provider interface. They do not import the web framework and do not open database connections.

Providers

Providers translate a capability call into an outbound request: build the URL, attach forwarded headers from request context, apply timeouts and circuit breakers, and turn the response into a typed result or a typed error. Providers never call the LLM and never read graph state.

Why one-directional imports matter

The rule is simple: a layer may import from layers below it, never above. In practice this buys three things.

  • Fast tests. Graph tests run with a fake provider and a stub LLM; no HTTP server, no database. Service tests run with in-memory repositories.
  • Replaceable edges. Moving from one LLM vendor to another, or from REST to gRPC for a domain API, touches one provider module.
  • Readable failures. When a stack trace shows a provider error, you know it is a network or upstream problem, not prompt logic.

A practical folder layout

app/
  api/          routes.py, deps.py, errors.py
  services/     chat_service.py, turn_admission.py
  graph/        build.py, state.py, nodes/, routers.py
  agents/       definitions/, policies/
  providers/    domain_client.py, llm_gateway.py, retrieval.py
  persistence/  collections.py, repositories/
  cache/        redis_keys.py, catalog_cache.py
  core/         settings.py, request_context.py, logging.py

Enforcing the rule automatically

Code review catches most violations, but a small import check in CI catches the rest. Tools such as import-linter for Python let you declare layer contracts and fail the build when, for example, app.graph imports fastapi, or app.providers imports app.graph.

[importlinter:contract:layers]
name = Orchestrator layers
type = layers
layers =
    app.api
    app.services
    app.graph
    app.providers

Common mistakes

  • Nodes that query Mongo directly. It feels convenient, but it couples graph logic to storage and makes checkpoints harder to reason about. Pass repositories in through the graph config instead.
  • Providers that format user messages. Wording belongs to compose. Providers return data and error codes.
  • Settings imported everywhere. Read settings once at startup and inject the values that each layer needs.

The layering is not about purity. It is about making sure that when something breaks at 2 a.m., the stack trace tells you which kind of problem you have.
