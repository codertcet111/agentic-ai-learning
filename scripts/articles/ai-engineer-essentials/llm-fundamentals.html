You do not need to train a model to build good AI products, but you do need an accurate picture of what a model does when you call it. Most surprising LLM behaviour stops being surprising once you hold four ideas in your head: tokens, context, sampling and the absence of a fact store.

Tokens, not words

A model reads and writes tokens: chunks of text produced by a tokenizer. In English a token averages about three quarters of a word, but numbers, code, rare names and non-Latin scripts often split into many more tokens. This matters because:

  • Pricing and limits are counted in tokens, so the same message costs more in some languages than others.
  • Models can struggle with tasks that depend on characters inside a token, such as counting letters or reversing strings.
  • Token counts, not character counts, decide whether your prompt fits.

The context window is the whole world

For each call, the model sees only what is in its context window: system prompt, conversation, tool results and retrieved documents. It has no memory of earlier calls unless you send that history again. Everything an assistant "remembers" is something your code chose to put back in the prompt (see agent memory).

Long windows help, but they are not free. Cost and latency grow with input size, and models tend to use information at the start and end of a long context more reliably than material buried in the middle. Put instructions and the most important facts where they are hard to miss, and keep the rest lean.

Generation is sampling

A model produces a probability distribution over the next token, picks one, appends it and repeats. Settings shape how it picks:

SettingEffectTypical use
TemperatureLower values make the most likely tokens more likely; higher values add varietyLow for extraction, planning and code; moderate for writing
Top-pRestricts choices to the smallest set of tokens covering probability pUsually leave at the default and tune temperature instead
Max output tokensHard cap on reply lengthAlways set it; it bounds cost and latency
Stop sequencesEnd generation when a string appearsSimple structured formats

Even at temperature zero, outputs are not guaranteed to be identical across runs or model versions. Design tests and pipelines that tolerate small variations (see golden cases).

Why models hallucinate

A model has no lookup table of facts. It generates text that is statistically plausible given its training and the context. When the context lacks the answer, the most plausible continuation is often a confident, specific and wrong one. This is the root of hallucination, and it shapes good architecture:

  • Facts about the user's own data come from tools, not from the model.
  • Facts about documents come from retrieval with citations.
  • The prompt tells the model what to do when information is missing: ask, or say it does not know.

Instructions are strong suggestions

System prompts steer behaviour well, but they are not enforcement. A determined user, or text inside a retrieved document, can sometimes pull the model off course. Anything that must always hold, such as permissions, limits or confirmation before a write, belongs in code around the model (see guardrails).

What this means day to day

  1. Measure prompts in tokens and watch them in traces.
  2. Use low temperature and structured outputs for decisions; save creativity for prose.
  3. Ground every factual answer in a tool result or a cited document.
  4. Keep hard rules in code, not in prompt wording.
