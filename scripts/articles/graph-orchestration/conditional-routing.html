In LangGraph, a conditional edge is a function that looks at the current state and returns the name of the next node. It is a small piece of code with a large effect: routers define the shape of every conversation. The single most useful rule for them is that they must be pure.

What "pure" means here

  • A router reads state and returns a node name (or a list of names for fan-out).
  • It does not write state. Writing is what nodes are for.
  • It does not call the LLM, the database or any network service.
  • Given the same state, it always returns the same answer.
def after_invoke(state: GraphState) -> Literal["plan", "compose", "fail"]:
    if state.get("error") and state["error"]["class"] == "upstream_unavailable":
        return "fail"
    if state.get("planner_calls", 0) >= MAX_PLANNER_CALLS:
        return "compose"
    return "plan"

graph.add_conditional_edges("invoke", after_invoke,
                            {"plan": "plan", "compose": "compose", "fail": "fail"})

Passing the explicit mapping as the third argument documents every possible destination. LangGraph's diagram output then shows the real edges, and a typo in a returned name fails at compile time rather than mid-conversation.

Why side effects in routers hurt

Suppose a router increments a retry counter "just to keep it simple". Three things break:

  1. Checkpoints miss it. State updates from a router are not recorded as a node step, so a resumed run sees a different counter from the original.
  2. Traces mislead. The span tree shows nodes. A decision that changed state between nodes is invisible.
  3. Tests get harder. A pure router is tested with a dictionary and one assert. A router with side effects needs fixtures and mocks.

If routing needs a computed value, add a tiny node that computes and stores it, then route on the stored value.

Route on structured fields

Routers should branch on typed fields that a node already set, such as plan.kind, error.class or pending_interaction_id, never on free text. A router that searches the model's reply for the word "sorry" is a bug that has not happened yet.

Testing every edge

@pytest.mark.parametrize("state,expected", [
    ({"error": {"class": "upstream_unavailable"}}, "fail"),
    ({"planner_calls": 12}, "compose"),
    ({}, "plan"),
])
def test_after_invoke(state, expected):
    assert after_invoke(state) == expected

These tests run in milliseconds and act as documentation. When product asks "what happens if the HR API is down?", the answer is a test name.

Fan-out

A router may return several node names to run branches in parallel, for example calling two read capabilities at once. Use this for genuinely independent reads, and make sure the state keys each branch writes either do not overlap or use reducers that merge safely.

Keep the graph readable

If a router has more than five or six outcomes, the decision probably belongs in a node, such as the planner, that writes a single next_action field. Routers stay simple when the hard thinking happens elsewhere.
