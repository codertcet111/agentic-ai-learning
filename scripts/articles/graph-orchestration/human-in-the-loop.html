Some actions should not happen just because a model decided they should. Cancelling an order, submitting a leave request, sending an email on someone's behalf: these need a human to say yes. Human-in-the-loop (HITL) is how the graph stops, waits and resumes safely.

Kinds of pause

KindWho respondsExample
ConfirmationThe user"Submit leave for 6–7 Nov?" [Confirm] [Edit] [Cancel]
FormThe userChoose approver, add a note
ChoiceThe userPick one of two matching employees
ApprovalAnother personManager approves an expense above a limit

The first three are covered by pending interactions. Approval by another person usually belongs in the domain system's own workflow. The orchestrator submits the request, and the approval happens in the HR or finance tool, not inside a paused graph that might wait for days.

LangGraph mechanics

LangGraph supports pausing with interrupt() inside a node. The run stops, the checkpoint records the interrupt, and the caller receives the interrupt payload. Resuming means invoking with the same thread id and Command(resume=value). Wrap this so the rest of your code deals with pending interactions, not raw interrupts:

def request_confirmation(state, config):
    pi = create_pending_interaction(kind="confirmation", summary=state["plan"], ...)
    answer = interrupt({"pending_interaction_id": pi.id})
    # execution continues here after resume
    return {"confirmed": answer["action"] == "confirm"}

Fingerprints against stale UI

A confirmation should be for exactly what the user saw. Compute a fingerprint, a hash of the capability id and the resolved arguments, and include it in the confirmation payload. On submit, recompute it from the checkpoint and compare. If anything changed (a re-plan adjusted the dates, a second tab edited the form) the submission is rejected and the user sees the current version. This prevents "I confirmed Friday but it booked Monday".

Expiry and transition messages

Every pause has an expiry. When it lapses:

  • Mark the interaction expired and delete its checkpoint.
  • Append a short assistant message: "That leave request wasn't submitted because the confirmation expired. Want me to set it up again?"
  • The client disables the stale buttons.

Without the message, users return the next day, click Confirm, get an error, and lose trust.

What not to pause for

Do not ask for confirmation on reads. "Do you want me to look up your balance?" adds friction with no safety benefit. Reserve HITL for writes, irreversible actions and genuine ambiguity. Users quickly learn to click through confirmations that appear too often, which defeats their purpose.
