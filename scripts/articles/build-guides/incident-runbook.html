When an AI assistant misbehaves in production, the cause is usually not "the model got worse". It is an upstream API, a deploy, a catalog change, a quota, or a data problem. This runbook helps on-call engineers find which one quickly.

1. Classify the incident

SymptomLikely areaFirst place to look
Errors for everyoneDeploy, database, LLM gatewayError tracker by release; gateway status
Errors for one featureOne upstream APIFailure records by capability_id
Slow turnsUpstream latency or LLM latencySpan durations: invoke vs llm.call
Wrong answers, no errorsCatalog, prompt or model changeRecent deploys; golden suite on current release
"It's stuck"Turn fence, worker crashTurn ledger for the conversation
Cost spikeLoop, prompt growth, abuseLLM calls per turn; usage by tenant

2. Follow one example end to end

  1. Request id → logs for that request.
  2. Conversation id → transcript and turn ledger in MongoDB.
  3. Trace id → span tree in the tracing tool: which node, which call, how long.
  4. Failure record → error class and runbook action.

One fully understood example is worth more than a dashboard of averages.

3. Separate upstream from model

If capability.invoke spans show 5xx responses, timeouts or open circuits, this is an upstream incident. Tell the owning team, confirm the assistant shows a "service busy" message, and do not change prompts. If invokes are healthy but plans are wrong, it is an orchestration or model issue. Check what changed: release, catalog hash, model version in the gateway.

4. Mitigations, from least to most drastic

  1. Disable a capability via feature flag. The agent stops offering it and says so.
  2. Pin the catalog to the previous hash if a catalog change caused it.
  3. Switch model alias in the gateway back to the previous model version.
  4. Roll back the orchestrator release.
  5. Turn the assistant off for affected tenants with a clear banner.

Each of these should be a documented, tested switch, not an improvised change during an incident.

5. Communicate

Users see the assistant, not your architecture. If a feature is down because of an upstream outage, a short status message in the chat UI prevents a flood of "the bot is broken" tickets.

6. After the incident

  • Add the failing scenario to the golden suite.
  • Add or tune the alert that should have fired first.
  • If the fix was a prompt change, add a test that would fail if the old prompt came back.
