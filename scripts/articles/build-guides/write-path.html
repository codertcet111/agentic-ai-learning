Reads can be wrong. Writes can be wrong and permanent. The first time your assistant can create, update or cancel something, the engineering bar goes up. This guide walks through adding one write, such as "submit a leave request", with the safeguards it needs.

The flow

User: "book Friday off"
  → plan: call_tool leave.request.create
  → resolve: dates resolved; approver from profile
  → request_input: confirmation card (summary + fingerprint)
User: [Confirm]
  → form_submission (pending id, revision, fingerprint)
  → invoke with explicit_action=true, operation_id=trn_87:step_4
  → compose: "Submitted. Request #5531 is waiting for approval."

Safeguard 1: confirmation is mandatory

Mark the capability requires_confirmation: true in the catalog. The graph always routes such capabilities through request_input before invoke. This is a graph rule, not a prompt instruction, so the model cannot skip it.

Safeguard 2: explicit action

The provider refuses any write unless explicit_action=true, and only the confirmation-resume path sets that flag. Even if a bug or an unexpected plan reached invoke directly, the write would not happen.

Safeguard 3: confirm exactly what runs

The confirmation shows a human-readable summary of the resolved arguments and carries a fingerprint of them. On submit, the server recomputes the fingerprint from the checkpoint. If they differ, the submission is rejected and a fresh confirmation is shown (see human-in-the-loop).

Safeguard 4: idempotent execution

The operation_id is built from the turn and step, never from model output, and sent as the upstream Idempotency-Key. Retries after timeouts and double-clicks on Confirm produce one record (see idempotency patterns).

Safeguard 5: honest results

Compose reports what the upstream returned: the new record's id and status, or the business error ("You already have leave booked on that day"). It never says "done" unless the provider returned success.

Tests to write

  • Happy path: one confirmation, one upstream call, success message.
  • Cancel: no upstream call.
  • Double submit of the same confirmation: one upstream call, and both responses show the same result.
  • Stale fingerprint: rejected with a fresh confirmation.
  • Free text while the confirmation is open: confirmation superseded, no write.
  • Upstream 409 conflict: business error explained, no retry.
  • Upstream timeout, then retry: one record created.
  • A user without permission: upstream 403 surfaced politely.

Tag all of these as write in the golden suite and require them to pass for every release.
