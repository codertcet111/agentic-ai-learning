An orchestrator that calls domain APIs on a user's behalf has to authenticate those calls somehow. The safest default is to forward the user's own credential with each request and never store it. The orchestrator then has no standing access of its own, and the domain applies exactly the permissions it would for the web app.

Forwarding versus a service account

Forward user tokenService account
PermissionsExactly the user'sWhatever the account has, often too much
Audit in domain logsShows the real userShows the service; needs extra headers
Blast radius if orchestrator is compromisedOnly active sessions' tokens, brieflyEverything the account can do
Works for background jobsNo; needs a user presentYes

For interactive chat, forwarding is the better default. Where the identity provider supports it, OAuth token exchange can produce a narrower, short-lived token for each downstream audience, which is better still.

The mechanics

  • Middleware copies the credential into request context (step 3). It never enters graph state, checkpoints or the prompt.
  • Providers attach it to each outbound call explicitly.
  • Shared HTTP clients have cookie persistence disabled, so one user's session cookie can never be sent with another user's request.
  • Outbound calls go only to configured upstream hosts. The model cannot supply a URL.

Never let the model see credentials

Prompts must not contain tokens, even "for context". Anything in a prompt can appear in the model's output, in traces and in provider logs. If a tool needs a credential, the provider adds it after the model has produced the arguments.

Redact at every exit

Credentials leak through side channels far more often than through the main path:

  • Exception messages from HTTP libraries that include request headers.
  • Debug logging of full request objects.
  • Error tracker events capturing local variables.
  • Trace attributes copied from request metadata.

Install redaction in the shared logging configuration, the error tracker's before-send hook and the trace exporter. Then test it: run a turn with a recognisable fake token and assert it appears in none of the outputs.

Expiry handling

Forwarded tokens expire. When an upstream returns 401, map it to auth_expired, tell the user to sign in again, and do not retry. Refresh tokens belong to the client application, not the orchestrator.
