Early prototypes call a model SDK directly from wherever it is needed. Six months later there are four SDKs, three retry implementations and model ids hard-coded in a dozen files. A single gateway prevents that. LiteLLM is a popular open-source choice: it exposes one OpenAI-style interface over many providers (OpenAI, Anthropic, Azure OpenAI, AWS Bedrock, Google Vertex AI and others) and can run as a Python library or as a proxy server.

What the gateway owns

  • Model aliases: code asks for planner or composer, and configuration maps that to a provider and model id.
  • Timeouts and retries: one policy, tuned per alias.
  • Fallbacks: if the primary deployment is rate-limited or down, try a secondary.
  • Accounting: token usage and cost for every call, sent to tracing.
  • Structured output plumbing: passing response schemas in whatever form each provider expects.

Aliases in configuration

# models.yaml
planner:
  model: anthropic/claude-sonnet-x       # illustrative ids; use your provider's
  timeout_s: 20
  max_output_tokens: 600
  fallbacks: [planner_backup]
planner_backup:
  model: bedrock/claude-sonnet-x
  timeout_s: 20
composer:
  model: openai/gpt-x-mini
  timeout_s: 25
  max_output_tokens: 900
router:
  model: openai/gpt-x-nano
  timeout_s: 8
  max_output_tokens: 80

Graph nodes never mention a provider. Moving the planner to a different model is a configuration change and an evaluation run, not a code change.

A thin wrapper in your code

class LLMGateway:
    async def complete(self, alias: str, messages: list[dict],
                       *, schema: type[BaseModel] | None, purpose: str,
                       ctx: RequestContext) -> LLMResult:
        cfg = self.models[alias]
        with tracer.generation(name="llm.call", purpose=purpose, model=cfg.model) as gen:
            resp = await litellm.acompletion(
                model=cfg.model, messages=messages,
                timeout=cfg.timeout_s, max_tokens=cfg.max_output_tokens,
                response_format=schema_format(schema),
            )
            gen.record_usage(resp.usage)
            return LLMResult.from_response(resp)

Even with LiteLLM underneath, keep your own small interface. It is the seam where tracing, the stub LLM for tests and per-purpose policies plug in.

Library or proxy?

  • Library: simplest; runs inside your service.
  • Proxy: one shared gateway for several services, with central keys, budgets and logging. Useful once more than one team calls models.

Roll out new models safely

Add the new model as a new alias, run the golden suite against it, compare traces and costs, then switch the alias per environment behind a flag. Keep the previous alias available for quick rollback.
