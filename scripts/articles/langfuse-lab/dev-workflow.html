When you ship an agentic backend, logs alone are not enough. You need one trace per user turn that shows routing, each graph step, every LLM call and every tool invoke, with latency, token usage and cost rolled up. Langfuse is an open-source LLM engineering platform built for exactly this, and this section of the site is a practical tour of using it while developing an agent.

What I set up before debugging any prompt

  1. Tracing in non-production first, with a structure capture mode: names, shapes, counts and timings, but no raw user text. Turn on richer capture only where your privacy review allows it.
  2. Tags and metadata on every trace: environment, release, conversation_id, turn_id and request_id, so support can jump from a log line to a trace.
  3. Consistent observation names: the root turn, router, each agent step, llm.call and capability.invoke. Charts and filters depend on these names, so pick them once.
  4. Eval runs in the same project, tagged or signed so they can be told apart from user traffic, so CI traces can be compared with real ones.
Dev tip: correlate X-Request-Id from API logs with the trace in Langfuse before you touch prompt wording. Half the time the problem is in a tool call, not the prompt.

The shape of a good trace

chat-turn                          (root: total latency, total cost, failure_reason)
├── route-request
│   └── llm.call  purpose=route    (small model)
├── agent-step: plan
│   └── llm.call  purpose=plan
├── agent-step: invoke
│   └── capability.invoke  leave.balance.read  (status 200, 180 ms)
├── agent-step: plan
│   └── llm.call  purpose=plan
└── agent-step: compose
    └── llm.call  purpose=compose

Langfuse models these as observations of different types. LLM calls are generations, which carry model, token usage and cost. Other steps are spans. With this shape, the trace view answers "where did the time and money go?" at a glance.

My daily loop

  1. Make a change: prompt, tool description or graph node.
  2. Run a handful of golden cases locally against a real model with tracing on.
  3. Open the newest traces and check the node sequence, number of LLM calls and token counts against yesterday's traces for the same cases.
  4. If something regressed, open the specific generation and read the input the model actually received.

The pages in this lab

  • Traces list: finding failed and slow turns.
  • Span tree: cost and time per graph node.
  • Trace detail: inputs, outputs, tokens and model metadata.
  • Turn checks: automated budgets as scores.
  • Masking and failures: privacy-safe export and failure reasons.
  • Local setup: getting your first trace.
