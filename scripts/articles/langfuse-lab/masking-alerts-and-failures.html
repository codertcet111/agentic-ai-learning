LLM traces are full of user text: questions, names, dates, sometimes things users should not have typed. Before any of it leaves your service, it should pass through a masking exporter. When masking misses something, you want to know without copying the sensitive value into yet another system.

How the masking exporter works

  1. Spans are collected in-process as usual.
  2. Before export, a processor walks every string attribute, input and output.
  3. Known identifiers (user ids, tenant ids) are replaced with keyed pseudonyms, an HMAC with a secret, so the same user always maps to the same placeholder but cannot be reversed.
  4. Pattern detectors replace emails, phone numbers, card-like numbers and national id formats with typed placeholders such as <EMAIL_1>.
  5. In structure mode, free text is dropped entirely and only its length and type are kept.

Residual alerts

After masking, a second, stricter scan checks whether anything that looks sensitive survived. If it finds something, it:

  • drops or blanks the affected field before export,
  • sends a throttled alert to the error tracker with the span name and the kinds of data found (for example "email, phone"), but never the values,
  • increments a metric so you can see whether residuals are rare accidents or a systematic gap.

Throttle the alerts per span name, or a single new prompt template can flood the channel.

Failure reasons on the root trace

Set a failure_reason on the root observation whenever a turn does not complete normally:

ReasonMeaning
run_timeoutThe turn exceeded its wall-clock budget
graph_errorAn unhandled exception inside the graph
run_failedA handled business failure (denied capability, validation error)
cancelledThe user or system cancelled an in-progress turn

With this as metadata you can filter traces by reason and chart each one separately. A rise in run_timeout needs a different response from a rise in graph_error.

Linking to support records

The root trace's metadata also carries the id of the matching failure record in MongoDB. Support works from the sanitized failure record; engineers follow the link into the trace when they need detail.
