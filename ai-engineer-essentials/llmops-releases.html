LLMOps: shipping prompt and model changes

LLMOps for shipping AI features safely: versioning prompts and configs, evaluating before release, canary rollouts, monitoring quality and cost, and rolling back model or prompt changes.

Shubham Mishra2 min read

In a normal web service, behaviour changes when code changes. In an AI system, behaviour also changes when a prompt is edited, a tool description is reworded, a retrieval index is rebuilt or the model provider ships a new version. LLMOps is the discipline of treating all of those as releases.

Version everything that changes behaviour

ArtifactHow to version it
Prompts and policiesIn the repository, reviewed like code
Tool catalogHash of the merged catalog, pinned per session
Model choiceAliases in configuration, mapped to exact model versions
Retrieval indexIndex version and embedding model id on every chunk
Evaluation setsIn the repository, next to the code they test

Tag every trace with these versions. When quality drops, you need to know which one moved.

Evaluate before you ship

  1. On every pull request: golden cases with a stub model, for plumbing (see LLM stub in CI).
  2. For prompt, tool or model changes: the same cases against the real model, several runs each, compared with the last approved baseline (see trace compare).
  3. Release gate: all safety and write cases pass; no significant regression in tool accuracy, cost or latency.

Roll out gradually

  • Feature flags per tenant or user group for new capabilities.
  • Canary releases: route a small share of traffic to the new prompt or model, compare scores and error rates, then widen.
  • Shadow runs for risky changes: run the new version on real inputs without showing its output, and compare offline.

Monitor what users actually get

After release, watch:

  • Error and failure rates by capability.
  • LLM calls, tokens and cost per turn.
  • Latency at p50 and p95.
  • Automated check scores and user feedback (see Langfuse scores).

Make rollback boring

Every behaviour change should be reversible in minutes: switch a model alias back, revert a prompt commit, pin the previous catalog hash, or turn off a flag. Practise it before you need it. Provider model updates deserve special care. Pin exact model versions where the provider allows it, and test new versions before switching the alias.

Write it down

Keep a short changelog of behaviour changes: what changed, why, which evaluation results supported it. Six months later, it is the only reliable answer to "when did the assistant start doing that?"
