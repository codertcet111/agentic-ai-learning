Embeddings and vector search

Embeddings and vector search for AI engineers: what an embedding captures, similarity metrics, approximate nearest-neighbour indexes, hybrid search, reranking and the mistakes that hurt retrieval quality.

Shubham Mishra2 min read

Retrieval, semantic search, deduplication, clustering and recommendation all rest on the same building block: turning text into vectors and finding vectors that are close together. Understanding that block well saves weeks of tuning later.

What an embedding is

An embedding model maps a piece of text to a fixed-length list of numbers, often a few hundred to a few thousand dimensions. Texts with similar meaning land close together in that space, so "How do I reset my password?" and "I forgot my login" end up near each other even though they share almost no words.

Embeddings capture meaning as the model learned it. They are strong on paraphrase and topic, and weaker on exact identifiers, numbers, negation and rare jargon. "Form HR-12" and "Form HR-21" can look almost identical to an embedding model.

Measuring closeness

  • Cosine similarity compares direction and ignores length. It is the most common choice.
  • Dot product equals cosine similarity when vectors are normalised, and is faster.
  • Euclidean distance is sometimes used by specific indexes.

Use whatever metric the embedding model was trained for; its documentation says which.

Searching millions of vectors

Comparing a query against every stored vector is exact but slow at scale. Vector databases use approximate nearest-neighbour (ANN) indexes such as HNSW (a layered graph) or IVF (clustered lists) to find very close matches quickly, trading a little recall for large speed gains. Index parameters control that trade-off, so tune them against your own recall measurements rather than accepting defaults blindly.

Options range from extensions in databases you may already run (pgvector for Postgres, vector search in MongoDB Atlas, OpenSearch) to dedicated vector databases. Keeping vectors next to your existing data simplifies filtering and access control (see vector metadata).

Hybrid search and reranking

Two techniques fix most retrieval quality problems:

  1. Hybrid search: run keyword search (BM25) and vector search, then merge the lists, for example with reciprocal rank fusion. Keywords catch exact codes and names; vectors catch paraphrases.
  2. Reranking: take the top 20 to 50 candidates and score each against the query with a cross-encoder or reranking model, which reads query and passage together. It is slower per item but much more precise, and you only run it on a short list.

Common mistakes

MistakeConsequence
Mixing vectors from different embedding modelsSimilarity scores become meaningless
Embedding huge chunksOne vector averages many topics and matches nothing well
Filtering permissions after searchLeaks and empty results (see RAG safety)
Using a fixed similarity threshold everywhereScores vary by model and domain; calibrate on your data
Never measuring recallQuality problems get blamed on the prompt

Choosing an embedding model

Public leaderboards are a starting point, not an answer. Build a small labelled set of real queries and the documents that should match, then compare two or three models on recall@k (see evaluating retrieval). Check language coverage, maximum input length, vector size (storage cost) and whether you can run it where your data is allowed to go.

Terms on this page

Embedding
A list of numbers representing the meaning of a piece of text.
ANN index
Approximate nearest-neighbour index, such as HNSW, for fast similarity search.
Reranker
A model that reorders a short list of search results by relevance.
