Turn ledger for developers

A developer's guide to the turn ledger: states, transitions, idempotent replays, stuck-turn sweeps and the queries to run when a chat turn hangs or duplicates.

2 min read

The turn ledger is the record of every user turn: when it started, what state it is in and how it ended. It is the first place to look when a user says "it's stuck" or "it did it twice". Step 5 covers the design. This article covers using it day to day.

States and transitions

pending ──► running ──► completed
               │  └───► failed      (error_class set)
               └──────► cancelled   (user abort or superseded)
running ──(sweeper, too old)──► failed (error_class: abandoned)

Transitions only move forward. Every update filters on the expected current state, so two workers can never both complete the same turn:

db.turn_ledger.update_one(
    {"_id": turn_id, "status": "running"},
    {"$set": {"status": "completed", "finished_at": now,
              "result_message_id": msg_id}})

If the update matches zero documents, something else already moved the turn. Log it and stop.

Queries you will run

// What is this conversation doing right now?
db.turn_ledger.find({conversation_id: cid}).sort({started_at: -1}).limit(5)

// Stuck turns across the system
db.turn_ledger.find({status: "running",
                     started_at: {$lt: new Date(Date.now() - 120000)}})

// Duplicate submissions from a client
db.turn_ledger.find({conversation_id: cid, client_request_id: rid})

// Failure mix in the last hour
db.turn_ledger.aggregate([
  {$match: {status: "failed", finished_at: {$gt: oneHourAgo}}},
  {$group: {_id: "$error_class", n: {$sum: 1}}}])

"It's stuck"

  1. Find the latest ledger entry for the conversation.
  2. If it is running and recent, the turn is genuinely in progress. Open its trace to see which node is slow.
  3. If it is running and old, the worker probably died. The sweeper will mark it failed. Check why the worker died (deploy, out-of-memory, timeout).
  4. If it is completed but the user saw nothing, the problem is delivery: streaming, client polling or a UI error.

"It did it twice"

Look for two ledger entries with different client_request_id values close together. That means the client sent two distinct requests, which is a UI double-submit issue. If you find two entries with the same id, your unique index is missing. Writes should still be protected by operation ids at the provider level (idempotency patterns), so check that next.

The sweeper

A job runs every minute, marks running turns older than the maximum turn duration as failed with error_class: abandoned, and clears the conversation fence so the user can continue. Alert if it sweeps more than a handful per hour, because that number tracks crashing workers.
