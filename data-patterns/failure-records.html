Failure records for support

Persist sanitized failure records for agent turns in MongoDB with stable error classes, correlation ids and safe context, so support can resolve issues without raw logs.

2 min read

When a turn fails, three audiences need to know: engineers (stack traces, in your error tracker), the user (a short, honest message) and support (what happened, in terms they can act on). Failure records serve the third audience, and they are often the missing piece.

The record

{
  "_id": "fr_…",
  "tenant_id": "acme",
  "conversation_id": "cnv_19b2",
  "turn_id": "trn_88",
  "request_id": "req_5f1…",
  "trace_id": "…",
  "error_class": "upstream_unavailable",
  "stage": "invoke_capability",
  "capability_id": "leave.request.create",
  "upstream_status": 503,
  "retryable": true,
  "user_message_key": "errors.service_busy",
  "detail": "HR API circuit open after 5 consecutive failures",
  "created_at": ISODate("…")
}

Stable error classes

The error_class field is the heart of the record. Keep the list short and documented:

ClassMeaningSupport action
auth_expiredUser token rejectedAsk user to sign in again
forbiddenUser lacks permission upstreamCheck role assignment
invalid_argumentsUpstream rejected inputCheck upstream validation message
upstream_unavailableTimeout, 5xx or open circuitCheck status page of that service
llm_invalid_outputSchema validation failed after repairEscalate to AI team with trace id
turn_timeoutTurn exceeded time budgetEscalate with trace id
internalUnexpected exceptionEscalate with request id

Each class maps to a runbook entry. When a new kind of failure appears often enough to deserve its own action, add a class. Do not let free-text messages become the classification.

Sanitize before writing

Failure records are read by more people than logs are, so they must be cleaner:

  • No request or response bodies from upstream. They may contain personal data.
  • No tokens or headers, and no raw exception messages from libraries that echo URLs with query strings.
  • detail is a sentence written by your code, not str(exception).

Indexes and retention

{ conversation_id: 1, created_at: -1 }
{ tenant_id: 1, error_class: 1, created_at: -1 }
{ created_at: 1 }  TTL 30 days

Using them

A small admin page that lists failures by conversation, with links to the trace and the transcript, saves engineers hours each week. Weekly counts by error_class and capability_id show which upstream integration needs attention, which is often more useful than any LLM metric.
