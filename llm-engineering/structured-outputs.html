Structured outputs in production

Get reliable structured outputs from LLMs in production: Pydantic schemas, provider-native JSON schema modes, semantic validation, a single repair attempt and safe failure.

2 min read

An agent's decisions travel between nodes as data. If that data is free text parsed with string matching, every model update is a risk. Structured outputs make LLM calls behave like typed function calls, mostly.

Three layers

  1. Constrain generation. Use the provider's structured output feature: tool or function calling with a JSON Schema, or a JSON-schema response format. This makes syntactically invalid JSON rare.
  2. Validate shape and types. Parse into a Pydantic model. Missing fields, wrong types and unexpected enum values are rejected here.
  3. Validate meaning. Check values against the turn's context: the capability exists in this session's catalog, the arguments match its parameter schema, the dates are real.

Design schemas for models

  • Keep them flat and small. Deeply nested optional objects are where models make mistakes.
  • Use enums for choices (Literal["call_tool", "need_input", "answer"]) rather than free strings.
  • Add field descriptions. Most providers pass them to the model, and they work like inline instructions.
  • Put a short reasoning or intent field before the decision fields when you want the model to think first. Models generate fields in order.
  • Avoid fields the model cannot know, such as ids it has not seen. Make those come from lookups.

Repair once, then fail safe

try:
    out = Schema.model_validate_json(raw, context=turn_ctx)
except ValidationError as err:
    raw2 = await gateway.complete(alias, repair_messages(raw, err), schema=Schema, purpose="repair")
    out = Schema.model_validate_json(raw2, context=turn_ctx)   # second failure raises

The repair prompt includes the original output and the validation errors, and asks for corrected JSON only. If that also fails, raise a typed llm_invalid_output error. The graph turns it into a short apology and a failure record. Never pass an unvalidated dictionary on to invoke_capability.

Measure it

Record a counter for first-try validation failures and repairs per schema and per model. A sudden rise after a model update or prompt change is an early warning, well before users notice. A healthy system has first-try failure rates well under one percent.

Watch for schema drift

Examples in the prompt, the Pydantic model, the stub fixtures and the golden cases must agree. When one changes, change them all in the same pull request. A prompt example showing a field that the schema no longer has is a reliable way to raise validation failures.
