Add RAG without breaking the graph

Add retrieval-augmented generation to an agent graph as a capability or a dedicated sub-agent, with citations, permission filtering and evaluation before launch.

Shubham Mishra2 min read

Sooner or later users ask questions that no API answers: "What's the policy on carrying over leave?", "How do I claim travel expenses?" The answer lives in documents. Retrieval-augmented generation (RAG) brings those documents into the conversation. Done carelessly, it also brings slow turns, huge prompts and confident misquotes. This step adds it without breaking the graph.

Option 1: retrieval as a capability

Expose search as a normal read capability:

{
  "id": "knowledge.search",
  "summary": "Search company policy documents. Use for questions about rules, procedures and entitlements, not for the user's own data.",
  "side_effect": "read",
  "parameters": {
    "type": "object",
    "required": ["query"],
    "properties": {
      "query":      {"type": "string"},
      "collection": {"type": "string", "enum": ["hr_policies", "it_help", "finance"]},
      "top_k":      {"type": "integer", "default": 5, "maximum": 10}
    }
  }
}

The planner decides when to search, just as it decides when to call any other tool. Retrieval shows up in traces as a capability.invoke, the results go to step_results, and compose receives the top chunks with their citations. This is the right default for assistants that mostly do actions and sometimes answer questions.

Option 2: a knowledge sub-agent

When questions are a large share of traffic, give them their own agent with a persona and policy tuned for answering from documents: always cite, quote numbers exactly, say "I couldn't find that" rather than guess. The router hands off to it. This keeps the action agent's prompt small and lets you tune and evaluate each separately.

Citations are not optional

Each chunk carries source_uri, title, section heading and page or anchor. Compose must cite what it used, and the UI renders citations as links. Citations let users verify answers. They also let you detect, in evaluation, when an answer cites a chunk that does not support it.

Permissions before ranking

Documents have audiences. The Saudi payroll policy should not appear for UK staff, and manager-only guidance should not appear for everyone. Filter by the principal's access scope in the retrieval query, before ranking, using metadata stored with each chunk. Filtering afterwards risks leaking titles or snippets through logs and traces. See RAG safety and ACL.

Keep chunks out of checkpoints

Retrieved text can be large. Store it in step_results and keep only chunk ids and a short summary in graph state. Checkpoints stay small and resumes stay fast (see keeping GraphState small).

Hybrid search for internal content

Company documents are full of acronyms, form codes and product names, such as "FMLA", "P60" or "form HR-12". Pure vector search handles these poorly because embeddings blur exact tokens. Combining lexical search (BM25) with vector search and fusing the rankings, for example with reciprocal rank fusion, is a reliable improvement for this kind of content.

Evaluate before you launch

Write 50 or so real questions with the document that should answer each. Measure whether that document appears in the top results (recall@k) before evaluating final answers. If retrieval misses, no prompt will fix it. The retrieval evaluation article covers the method.

Try this: Measure retrieval recall before tuning compose prompts—bad chunks cannot be composed away.
