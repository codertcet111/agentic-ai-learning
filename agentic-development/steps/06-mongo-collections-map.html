Map Mongo collections to roles

A map of the MongoDB collections an orchestration service needs, what each one owns, and how to declare indexes once and create them at startup.

Shubham Mishra2 min read

An orchestration service needs more storage than "a messages table". Each concern gets its own collection, so documents stay small, indexes stay targeted, and you can set a different retention policy per concern.

The collection map

CollectionOwnsTypical retention
sessionsPrincipal, tenant, expiry, pinned catalog hashDays (TTL)
conversationsThread status, revision, limits, titleMonths
messagesOne document per message, ordered by sequenceMonths, per policy
turn_ledgerLifecycle of each turn, idempotency keysWeeks
pending_interactionsForms and confirmations waiting for the userHours to days
graph_checkpointsSerialized graph state for resumeShort; delete when a turn completes
step_resultsLarge tool outputs stored by referenceWeeks
usage_countersTokens and invokes per tenant per dayMonths
failure_recordsSanitized errors for supportWeeks
catalog_versionsMerged tool catalogs by hashUntil no session references them

One module for names and indexes

Declare every collection name and its indexes in a single module. Nothing else in the codebase hard-codes a collection string.

from pymongo import IndexModel, ASCENDING as A, DESCENDING as D

MESSAGES = "messages"
TURN_LEDGER = "turn_ledger"

INDEX_SPECS = {
    MESSAGES: [
        IndexModel([("conversation_id", A), ("sequence", A)], unique=True),
        IndexModel([("conversation_id", A), ("idempotency_key", A)],
                   unique=True,
                   partialFilterExpression={"idempotency_key": {"$type": "string"}}),
    ],
    TURN_LEDGER: [
        IndexModel([("conversation_id", A), ("client_request_id", A)], unique=True),
        IndexModel([("status", A), ("started_at", A)]),
    ],
}

Create indexes at startup, not at import

Run create_indexes in the application's startup hook (FastAPI's lifespan, for example). Doing it at import time slows tests, fails when the database is unreachable, and runs once per worker process in unpredictable order. Index creation is idempotent, so running it on every boot is safe.

@asynccontextmanager
async def lifespan(app):
    db = connect()
    for name, specs in INDEX_SPECS.items():
        await db[name].create_indexes(specs)
    yield
    db.client.close()

Partial unique indexes

The idempotency_key index above uses a partial filter so uniqueness applies only when the field is a string. System messages without a key do not collide with each other. Without the filter, every document missing the field would count as null and the second one would fail to insert.

TTL for short-lived data

Sessions, checkpoints and expired pending interactions are good TTL candidates. A TTL index on an expires_at field with expireAfterSeconds: 0 lets MongoDB delete documents at the time you choose. The TTL monitor runs about once a minute, so do not rely on it for exact timing. Your code should still check expires_at on read.

Keep the map current

When someone adds a field that queries filter on, they add the index in the same pull request. Drift between the code's queries and the declared indexes shows up as slow queries under load, which is the most expensive time to find it.

Try this: Keep INDEX_SPECS as the single source of truth; drift between model and index causes silent prod failures.
