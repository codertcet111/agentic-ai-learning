Step 10 — Provider adapters and invoke

Build provider adapters that invoke domain capabilities with shared HTTP pools, explicit timeouts, bounded retries, circuit breakers and typed error envelopes.

2 min read

Providers are the orchestrator's hands. When the planner decides to call leave.balance.read, a provider turns that into an HTTP request, applies the right credentials and timeouts, and turns whatever comes back into something the graph can reason about. It is unglamorous code, and most production incidents in agent systems start here.

One interface

class Provider(Protocol):
    async def invoke(self, capability: Capability,
                     arguments: dict, ctx: RequestContext,
                     *, operation_id: str | None = None) -> InvokeResult: ...

@dataclass
class InvokeResult:
    ok: bool
    data: dict | None = None
    error: AppError | None = None
    status: int | None = None
    latency_ms: int = 0

Graph nodes only ever see InvokeResult. They never catch httpx exceptions or read raw status codes.

The HTTP machinery

  • Shared client per upstream, created at startup, with connection pooling and cookie persistence turned off (see step 3).
  • Explicit timeouts: a short connect timeout (around 2 seconds) and a read timeout that fits the endpoint. A balance lookup should not wait 60 seconds.
  • Bounded retries on connection errors and 502/503/504 only, with jittered backoff, and only for reads or for writes that carry an operation id.
  • Circuit breaker per upstream: after N consecutive failures, fail fast for a cool-down period instead of piling up timeouts.

Typed errors

Map upstream responses to a small set of error classes the planner and compose step understand:

UpstreamError classWhat compose says
400 / 422invalid_argumentsAsks the user to correct the input
401auth_expiredAsks the user to sign in again
403forbiddenExplains that they lack access, without detail
404not_foundSays the item could not be found
409conflictExplains the business conflict from the error body
5xx, timeout, open circuitupstream_unavailableSays the service is busy; try later

Writes and operation ids

Every write capability carries an operation_id derived from things the model cannot invent: the turn id and the step index. Send it upstream as an Idempotency-Key header. If the user double-taps, or a retry fires after a timeout that actually succeeded, the upstream sees the same key and returns the original result instead of creating a second leave request.

Never derive operation ids from model-generated arguments. Two slightly different phrasings of the same request would produce two different ids and two writes.

Explicit action

Writes also require an explicit_action flag that only the confirmation path sets (step 8 and the write confirmation article). The provider refuses a write without it, even if the planner asks. This is a cheap, local guard against a planner that skips the confirmation step.

Observability

Wrap every invoke in a capability.invoke span with capability id, provider, status, latency and error class, but not arguments or response bodies by default. That is enough to tell, at a glance, whether a slow turn was the model or the network.

Developer POV: Unit-test circuit breaker open path returns typed AppError, not raw httpx exceptions.
