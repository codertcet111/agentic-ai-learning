Step 16 — Presentation modes and bilingual compose

Let structured results render as tables, cards or forms through presentation modes, while compose still produces bilingual fallback text for every reply.

2 min read

Many good assistant answers are not paragraphs. A list of upcoming leave is a table. An order is a card with a status badge. A choice between two approvers is a set of buttons. Presentation modes let the graph say how a result should be shown, and let the client render it natively.

The presentation block

{
  "presentation": {
    "mode": "table",                     // text | table | card | list | form | chart
    "source_step_result_id": "sr_…",
    "columns": [
      {"key": "type",  "label": {"en": "Type",  "ar": "النوع"}},
      {"key": "start", "label": {"en": "Start", "ar": "البداية"}},
      {"key": "days",  "label": {"en": "Days",  "ar": "الأيام"}}
    ]
  },
  "text": {
    "en": "You have two upcoming leave periods.",
    "ar": "لديك فترتا إجازة قادمتان."
  }
}

The client picks a renderer by mode. If it does not support that mode (an older app version, a voice channel, an email digest) it shows the text.

Text is never optional

Every assistant message carries fallback text in each supported language, even when the UI is primary. Reasons:

  • Screen readers and accessibility tools need words.
  • Notifications and message previews show text only.
  • Transcripts sent to the LLM in later turns are built from text, not from tables.
  • Older clients cannot render new modes.

The text should summarize the result, not repeat it. "You have two upcoming leave periods" next to a table is right. Writing out every row in prose underneath the same table is noise.

When compose runs

For pure data results with a clear mode, a template can produce the fallback text without an LLM call ("You have {n} upcoming leave periods"). Compose runs when the answer needs judgement: explaining a conflict, combining two results, answering a "why" question. The response_finalized flag in state ensures only one node produces the final reply, so a later node cannot accidentally compose again and overwrite it.

Bilingual compose

If your product serves more than one language, the compose schema should require every language field, as in ComposePayload in step 13. Generate both in one call. The model keeps the meaning aligned and you avoid a second round trip. Right-to-left languages such as Arabic need the client to set dir="rtl" on the text container, and tables need their column order mirrored. That is client work, but the server should mark the locale on every message so the client knows. See bilingual compose for prompt details.

Testing

Snapshot-test the presentation block and both language strings for each golden case. When a capability's response shape changes, the snapshot diff shows exactly which columns moved, before a user sees an empty table.

Developer POV: Snapshot compose en/ar strings in tests when UI uses structured renderers.

Terms on this page

Presentation mode
Hint telling the client how to render a capability result.
Fallback text
Plain-language summary if the rich UI cannot load.
Locale
User language preference driving compose output.
