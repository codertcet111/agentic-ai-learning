Trace requests, nodes, and LLM calls

Trace every agent turn from request id to conversation, graph run, nodes, LLM calls and tool invokes, with pseudonymized identifiers and no secrets in span attributes.

Shubham Mishra2 min read

When a user says "the bot gave me a weird answer yesterday afternoon", you need to find that exact turn and see every decision it made. That is what tracing is for. The goal of this step is one trace per turn, with a predictable shape, linked to your logs and your database.

The correlation chain

X-Request-Id  ──► structured logs
     │
     └─► conversation_id + turn_id ──► Mongo (messages, turn_ledger, failure_records)
              │
              └─► trace_id ──► tracing backend (Langfuse, OpenTelemetry collector, APM)

Every log line carries request_id. The turn ledger stores trace_id. The trace's metadata carries conversation_id and turn_id. From any one of them, you can reach the others in a single search.

Span names

Agree on a small, fixed vocabulary and use it everywhere:

SpanParentKey attributes
agent.requestrootroute, tenant (pseudonymized), locale, catalog_hash
langgraph.runagent.requestthread_id, resumed (bool)
langgraph.nodelanggraph.runnode name, step index
llm.callnodemodel, purpose, input/output tokens, cost, latency
capability.invokenodecapability id, provider, status, error class, latency

The purpose attribute on LLM calls (route, plan, resolve, compose) is what lets you answer "where do our tokens go?" with a single grouped query.

OpenTelemetry or vendor SDK?

Both work. OpenTelemetry gives you one instrumentation layer that can export to several backends, including APM tools and LLM-specific ones. Langfuse and similar tools accept OpenTelemetry spans and also offer their own SDKs with LLM-aware fields such as token usage and cost. A common setup is OpenTelemetry for request and infrastructure spans, with LLM spans enriched with the attribute names the LLM observability tool expects. The Langfuse Lab section walks through the UI side.

What never goes in a span

  • Tokens, cookies, API keys and authorization headers.
  • Raw user identifiers. Use a keyed hash (HMAC) so the same user maps to the same pseudonym without being reversible.
  • Full prompts and outputs in production, unless your privacy review has approved a masked capture mode.

Enforce this in the exporter, not by asking every developer to remember. A masking processor that runs before export is the single point of control.

Alerts that pay off

  • Planner failure rate above baseline: usually a catalog or schema change, not the model.
  • 403 spike on capability.invoke: permission drift between the catalog and upstream.
  • LLM calls per turn p95 rising: loops or ambiguous tool descriptions.
  • Turn duration p95 above budget: check provider latency before blaming the model.

Sampling

Trace 100% of turns in development and staging. In production, trace all errored turns and a sample of successful ones if volume or cost demands it. Make the sampling decision at the root span, so you never keep half a trace.

Try this: Link Datadog APM (if used) with Langfuse via shared request_id in logs.

Terms on this page
