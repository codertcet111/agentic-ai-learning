Append messages, don't mutate arrays

Store chat transcripts as append-only message documents with a per-conversation sequence and idempotency keys instead of growing arrays inside one document.

Shubham Mishra2 min read

The tempting first design stores a conversation as one document with a messages array. It works until it does not: the 16 MB document limit, write conflicts when two writers push at once, and expensive rewrites of the whole document for every new message.

The design that scales is one document per message, appended and never edited.

Message document

{
  "_id": "msg_…",
  "conversation_id": "cnv_…",
  "sequence": 27,
  "role": "assistant",                 // user | assistant | system | tool
  "turn_id": "trn_…",
  "idempotency_key": null,
  "content": {
    "text": "You have 12 leave days left this year.",
    "blocks": [
      {"type": "table", "columns": ["Type", "Days"],
       "rows": [["Annual", 12], ["Sick", 5]]}
    ]
  },
  "tool_calls": [{"id": "tc_1", "capability": "leave.balance.read",
                  "step_result_id": "sr_…"}],
  "created_at": "…"
}
  • sequence is a per-conversation counter. Ordering by it gives a deterministic transcript, regardless of clock skew between servers.
  • content.blocks holds structured UI elements (tables, cards, forms) separately from plain text, so clients can render them natively and accessibility tools still get readable text.
  • tool_calls link to step_results by id instead of embedding large payloads.

Allocating sequence numbers

Because turns are fenced (step 5), only one writer appends to a conversation at a time, so you can safely allocate the next sequence from the conversation document:

conv = conversations.find_one_and_update(
    {"_id": cid, "active_turn_id": turn_id},
    {"$inc": {"message_count": 1}},
    return_document=ReturnDocument.AFTER)
seq = conv["message_count"]
messages.insert_one({..., "sequence": seq})

The unique index on (conversation_id, sequence) is the safety net. If a bug ever lets two writers in, one insert fails loudly instead of silently interleaving.

Idempotent appends

User messages carry a client-generated idempotency_key. A retry with the same key hits the partial unique index and you return the existing message instead of creating a duplicate. This is what lets a mobile app queue messages offline and replay them safely.

Why never update

Append-only storage makes three things simple:

  • Audit. What the user saw is exactly what is stored.
  • Replay. You can rebuild the LLM context for any past turn by reading messages up to that turn's sequence.
  • Sync. Clients fetch "messages after sequence N" and never need to diff.

When something must change, such as a user deleting a message or an admin redacting content, append a tombstone or redaction event and let readers apply it. For legal deletion requests, a separate job removes content fields and keeps the skeleton.

Reading for the model

The transcript you store is not the transcript you send to the LLM. A window builder reads the last N messages by sequence, drops UI-only blocks, swaps tool results for short summaries and stays within a token budget. Keeping storage and prompt construction separate means you can change the window strategy without migrating data. See token window management.

Try this: Never UPDATE message documents; append-only makes replay and audit trivial.

Terms on this page

Idempotency key
Client-supplied token so retries do not duplicate messages.
Sequence
Monotonic integer establishing deterministic transcript order.
Payload
Structured message body including tool calls and UI metadata.
