Golden evals and regression gates

Freeze agent behaviour with golden JSON cases covering routing, tool choice, multi-turn flows and safety, run in CI with stubbed models and nightly against real ones.

Shubham Mishra2 min read

The last step closes the loop. Without evaluation, every prompt tweak, model upgrade and catalog change is a guess. With a golden suite, it is a diff.

What a golden case is

{
  "id": "leave.balance.basic.en",
  "tags": ["leave", "read", "single-turn", "en"],
  "locale": "en",
  "principal": "fixture:employee_basic",
  "turns": [
    {
      "user": "how many leave days do I have left?",
      "expect": {
        "route": "model",
        "capabilities": ["leave.balance.read"],
        "no_capabilities": ["leave.request.create"],
        "response_contains_any": ["12", "twelve"],
        "max_llm_calls": 3
      }
    }
  ]
}

One file per scenario. Each turn states the user input and expectations that can be checked mechanically: which route, which capabilities were called (and which were not), presentation mode, and limits on calls and latency.

What to cover

  • Routing: recipes hit exactly; near-misses go to the model.
  • Tool choice: the right capability for common phrasings, in every supported language.
  • Ambiguity: two matching entities lead to a choice, never a silent pick.
  • Multi-turn flows: form, free-text supersede, resubmission.
  • Writes: confirmation always shown; double submit creates one record.
  • Safety: requests for other people's data refused; prompt injection in documents ignored.
Write at least five cases for every capability that changes data. Writes are where incidents happen.

Two ways to run it

  1. On every pull request, with a stub LLM. The stub returns the planner and compose outputs recorded in the case. This checks plumbing: routing, persistence, pending forms, provider calls against fakes. It is fast and deterministic, and needs no API keys.
  2. Nightly, with real models. The same cases run against the real model through your gateway, with fake or sandbox upstreams. This checks behaviour: does the model still choose the right tool? Results are compared with the last good run.

Assertions: exact where possible

Capability ids, routes, presentation modes and call counts are exact checks. Free text is not. For wording quality, use either "contains any of" checks for key facts or a rubric-scored judge model (see LLM-as-judge). Never use a judge model to decide whether a safety case passed.

Reports and gates

The runner writes a summary (pass/fail per case and tag) plus a diff against the previous run: which cases changed node sequence, which used more tokens, which got slower. Publish it as a Markdown or HTML artifact in CI.

Gate releases on tags. Every case tagged safety or write must pass. For the rest, set a threshold and review regressions by hand.

Growing the suite

Every production incident becomes a case. Every confusing support ticket becomes a case. After a few months the suite is the most accurate description of what your assistant actually does, more accurate than any design document. That is the point.

Terms on this page

Golden case
Recorded scenario with expected orchestration behavior.
Stub LLM
Deterministic model double returning canned structured output.
Regression gate
CI job that fails when behavior drifts from approved baselines.
