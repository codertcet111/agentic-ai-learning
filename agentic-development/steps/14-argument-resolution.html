Step 14 — Resolve arguments without smuggling ids

Resolve tool arguments by enriching context with lookups and replanning, rather than letting resolver code quietly choose entity ids on the model's behalf.

2 min read

The planner says "create a leave request for next Friday, approver Sara". The capability needs start_date, end_date and approver_id. Argument resolution is the step that bridges the gap, and it is where agents most often make confident mistakes.

Three sources of argument values

  1. User text and transcript: "next Friday", "the same dates as last time".
  2. Previous step results: an order id returned by a search two steps ago.
  3. Lookups: capabilities that turn a name into an id, such as employees.search.

Deterministic first

Anything that can be computed without a model should be. Relative dates are resolved in code using the user's timezone from request context, with a library like dateparser or your own rules, never by asking the LLM what day it is. Enum values are normalized with a mapping table. The LLM fills only what remains.

Lookups enrich; they do not choose

When a parameter needs an entity id, the resolver runs the lookup capability and appends the whole result to lookup_trace:

{"lookup": "employees.search", "query": "Sara",
 "results": [
   {"id": "emp_201", "name": "Sara Khan",  "dept": "Finance"},
   {"id": "emp_388", "name": "Sara Lopez", "dept": "Engineering"}
 ]}

Then the graph replans. With both candidates in front of it, the planner either picks one because the context makes it obvious (the user's manager is in Engineering), or returns need_input and the user picks from a list.

Code review rule: no resolver may set an entity id that does not appear in lookup_trace or a previous step result. A resolver that takes results[0] is a bug, even when it usually works.

Why not let the resolver pick?

Because "usually" is the problem. With two Saras, picking the first sends a leave request to the wrong person and nobody notices until they ask why. Making ambiguity visible to the planner, and through it to the user, costs one extra LLM call. Silent mistakes cost much more.

Grounding writes

Before a write, run grounding checks in code against domain rules the orchestrator can verify cheaply: end date after start date, quantity positive, date inside the open payroll period. Grounding does not replace upstream validation. It catches obvious errors before the confirmation form, so users do not confirm something that is certain to fail.

Unresolved arguments become forms

If arguments remain unresolved after lookups, the resolver returns them in unresolved. The planner turns that into a pending form with the resolved values prefilled. The user sees "Approver: [choose]" next to the dates already filled in, which is both faster and more accurate than another round of chat.

Developer POV: Code review rule: no resolver may set an entity id without lookup_trace entry.
