Wire LangGraph with a checkpointer

Wire a LangGraph StateGraph with typed state, async nodes, pure routing functions and a MongoDB checkpointer, compiled once at application startup.

Shubham Mishra2 min read

With storage, context and providers in place, the graph itself is a fairly small piece of code. The aim of the skeleton is to keep it that way: typed state, plain async functions as nodes, pure functions as routers, and a checkpointer so runs survive restarts and pauses.

Typed state

from typing import TypedDict, Literal, Annotated
import operator

class GraphState(TypedDict, total=False):
    conversation_id: str
    turn_id: str
    user_text: str
    plan: dict | None
    arguments: dict | None
    lookup_trace: Annotated[list[dict], operator.add]
    step_result_ids: Annotated[list[str], operator.add]
    pending_interaction_id: str | None
    response: dict | None
    response_finalized: bool
    error: dict | None

The Annotated[..., operator.add] fields are reducers: when a node returns a list for that key, LangGraph appends it rather than replacing it. Use reducers for accumulating traces. Use plain fields for values that should be overwritten.

Notice what is absent: tokens, headers, raw tool payloads. Those live in request context and in step_results.

Nodes and routers

async def plan_next_step(state: GraphState, config) -> dict:
    deps = config["configurable"]["deps"]
    plan = await deps.planner.plan(state, config["configurable"]["request_context"])
    return {"plan": plan.model_dump()}

def after_plan(state: GraphState) -> Literal["resolve", "ask", "compose"]:
    kind = state["plan"]["kind"]
    return {"call_tool": "resolve", "need_input": "ask"}.get(kind, "compose")

Nodes return partial state updates. Routers read state and return the next node's name. Routers never call the LLM, never write state and never perform I/O. That keeps every edge in the graph testable with a plain dictionary.

Building and compiling

from langgraph.graph import StateGraph, START, END

def build_graph(checkpointer):
    g = StateGraph(GraphState)
    g.add_node("load_session", load_session)
    g.add_node("plan", plan_next_step)
    g.add_node("resolve", resolve_arguments)
    g.add_node("invoke", invoke_capability)
    g.add_node("ask", request_input)
    g.add_node("compose", compose_response)

    g.add_edge(START, "load_session")
    g.add_edge("load_session", "plan")
    g.add_conditional_edges("plan", after_plan)
    g.add_edge("resolve", "invoke")
    g.add_edge("invoke", "plan")       # replan with new results
    g.add_edge("ask", END)
    g.add_edge("compose", END)
    return g.compile(checkpointer=checkpointer)

Compile once

Compile the graph in the application startup hook, after repositories and the checkpointer exist, and store it on the app. Compiling per request wastes CPU and, more importantly, hides configuration mistakes until the first user hits them. Compile-time failures at startup are the cheapest kind.

Checkpointer and thread ids

LangGraph offers a MongoDB checkpointer (langgraph-checkpoint-mongodb) along with Postgres and others. Each run uses a thread_id in its config to identify the checkpoint lineage. Use a value that identifies the workflow, typically the turn id or the pending interaction's origin turn. Do not encode tenant or user ids in it, and never auth.

result = await app.state.graph.ainvoke(
    {"conversation_id": cid, "turn_id": tid, "user_text": text},
    config={"configurable": {
        "thread_id": tid,
        "request_context": ctx,
        "deps": deps,
    }},
)

Bounding the loop

The invoke → plan edge creates a loop. Set recursion_limit in the run config to a sensible ceiling (for example 12 steps), and also count planner calls in state so compose can explain gracefully when a turn needed too many steps. Either limit firing in production is a signal worth alerting on.

Try this: Compile graph once; if compile runs per request, you have a performance incident waiting.
