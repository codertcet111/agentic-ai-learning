Merge and pin the capability catalog

Merge capability catalogs from upstream services, normalize their schemas, hash the result and pin that version per session so tools never change shape mid-conversation.

Shubham Mishra2 min read

The planner can only choose tools it has been told about. The capability catalog is that list: every tool with its id, description, parameter schema, owning provider and risk class. Getting it right is half of tool-calling quality. Keeping it consistent is the other half.

One capability entry

{
  "id": "leave.request.create",
  "summary": "Create a leave request for the current employee.",
  "provider": "hr-api",
  "method": "POST",
  "path": "/v2/leave/requests",
  "side_effect": "write",              // read | write | destructive
  "requires_confirmation": true,
  "parameters": {
    "type": "object",
    "required": ["leave_type", "start_date", "end_date"],
    "properties": {
      "leave_type": {"type": "string", "enum": ["annual", "sick", "unpaid"]},
      "start_date": {"type": "string", "format": "date"},
      "end_date":   {"type": "string", "format": "date"}
    }
  },
  "permissions": ["leave.request.create"]
}

Where catalogs come from

The best catalogs are published by the services that own the capabilities, as a JSON document at a well-known endpoint or as part of an OpenAPI spec with extension fields. The orchestrator does not hand-write tool definitions for APIs it does not own. When the HR team adds a field, their published catalog changes and the orchestrator picks it up.

Merge, normalize, hash

  1. Fetch each upstream catalog.
  2. Normalize into internal typed models: consistent id format, JSON Schema draft, defaults filled in, unknown fields dropped.
  3. Validate: ids unique across providers, schemas compile, every write capability declares requires_confirmation.
  4. Hash the canonical JSON (sorted keys) with SHA-256. That hash is the catalog version.
  5. Store the merged catalog in catalog_versions keyed by hash, and cache it in Redis.

Pin per session

When a session is created it records the current catalog hash. Every turn in that session plans against that exact version. Without pinning, a deploy that renames a parameter in the middle of a conversation can leave a paused form pointing at a schema that no longer exists. With pinning, old sessions finish on the old version and new sessions get the new one.

Put the catalog hash in every trace. When support asks "why did the bot not offer X?", the first answer is often "that session was pinned to a catalog from before X shipped."

Refreshing

Refresh on a schedule (every few minutes) or on a webhook from upstream deploys. If a fetch fails, keep serving the last good version and raise an alert. Never publish a partially merged catalog because one provider timed out.

Per-user filtering

The merged catalog is the superset. Before planning, filter it down to what this principal may use (the session's capabilities list) and what this agent persona should see. A payroll assistant does not need inventory tools in its prompt, even if the user is allowed to use them elsewhere. Smaller tool lists improve tool selection accuracy and reduce input tokens.

Coverage reports

Run a small report in CI that lists capabilities in the catalog that no agent exposes, and agent references to capabilities that no longer exist. The first means features that users cannot reach. The second means runtime errors waiting to happen.

Try this: Log catalog hash on each turn in traces; support can see if a user pinned an old tool list.
