Step 4 — Model sessions and conversations

Model sessions (who is chatting and under what scope) separately from conversations (individual chat threads with revisions, limits and lifecycle).

2 min read

Chat products tend to start with a single "chat" table and regret it. Two concepts hide inside it, and they have different lifetimes.

  • A session answers who is chatting and under what terms: principal, tenant, expiry, and which version of the tool catalog they were given.
  • A conversation answers which thread: its messages, revision counter, limits and whether it is still open.

One session may own many conversations. A conversation belongs to exactly one session.

Session document

{
  "_id": "ses_7f3a…",
  "principal_id": "emp_1042",
  "tenant_id": "acme",
  "created_at": "2026-10-01T09:12:00Z",
  "expires_at": "2026-10-01T21:12:00Z",
  "catalog_hash": "c9e1…",
  "capabilities": ["leave.balance.read", "leave.request.create"],
  "locale": "en"
}

Notice what is missing: no access token, no cookies, no email. The session stores opaque identifiers and the metadata the orchestrator needs to make decisions. The token arrives fresh with every request (step 3).

The catalog_hash pins the tool catalog version for the session. If a deploy changes a tool's schema in the middle of someone's chat, their session keeps using the version it started with until it expires (step 9).

Conversation document

{
  "_id": "cnv_19b2…",
  "session_id": "ses_7f3a…",
  "status": "active",
  "revision": 14,
  "message_count": 27,
  "max_messages": 200,
  "title": "Leave next week",
  "created_at": "…",
  "updated_at": "…"
}
  • revision increases on every accepted turn. Clients send the revision they last saw; the server rejects stale writes. This is the foundation for turn admission in step 5.
  • status is active or deactivated. Deactivation is terminal: the user hit the message limit, closed the thread, or an admin ended it.
  • message_count and max_messages cap runaway threads and the token costs that come with them.

Lifecycle

  1. User signs in to the host app. The host calls the orchestrator to create or refresh a session.
  2. User opens the assistant. The client lists conversations for the session, or creates a new one.
  3. Each message is a turn against one conversation and one expected revision.
  4. Session expiry blocks new turns, but conversations remain readable for history.

Indexes

sessions:      { principal_id: 1, expires_at: -1 }
               { expires_at: 1 }  with TTL if you purge old sessions
conversations: { session_id: 1, updated_at: -1 }
               { status: 1, updated_at: -1 }

Edge cases worth testing

  • Two browser tabs on the same conversation: the second sends a stale revision and must get a clear, recoverable error.
  • Session expires mid-turn: the turn in flight finishes; the next one is refused with a re-authenticate signal.
  • Conversation reaches its limit: the final assistant message tells the user to start a new thread, and the UI disables input.

Keeping sessions and conversations apart makes all three of these straightforward. Mixing them makes each one a special case.

Developer POV: Integration-test conversation revision rejection before you ship mobile offline queue.

Terms on this page

Session document
Durable record of a signed-in chat principal and expiry.
Conversation revision
Monotonic counter used to reject stale client writes.
Deactivation
Terminal state when limits are hit or the user ends the thread.
