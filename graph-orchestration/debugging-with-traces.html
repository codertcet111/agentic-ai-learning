Debugging graph bugs with traces

A practical method for debugging LangGraph agent bugs with traces: reproduce, find the request id, walk the span tree and diff node sequences against a known-good run.

2 min read

Agent bugs rarely produce stack traces. They produce answers that are slightly wrong, a tool that was not called, or a turn that took twelve seconds instead of three. Traces are how you turn "the bot was weird" into a specific node and a specific input.

Step 1: get an identifier

Ask for, or look up, one of: the request id from the client, the conversation id, or the approximate time and user. Your logs map any of these to a trace id (step 18). Never start debugging by guessing which turn it was.

Step 2: read the node sequence

Open the trace and list the nodes in order. Compare with what you expected:

Expected:  load_session → route → plan → resolve → invoke → plan → compose
Actual:    load_session → route → plan → compose

Here the planner answered directly without calling the tool. Now you know which node to examine, and that node's LLM call is where the problem lies.

Step 3: inspect the decision

Open the planner's LLM observation and check, in order:

  1. Was the right tool in the prompt? Check the capability list. If the tool is missing, the cause is catalog filtering or session pinning, not the model.
  2. Was the tool's description clear? Two tools with overlapping descriptions cause most wrong-tool bugs.
  3. What did the model return? Read the structured output. A kind: "answer" with an invented balance points to a policy gap: the prompt did not say to always use the tool for user data.
  4. What was in the transcript window? Sometimes an earlier assistant message contains a number the model happily reused.

Step 4: reproduce locally

Turn the failing input into a golden case. Run it with the real model a few times. LLM behaviour is probabilistic, so a bug that appears in two runs out of ten is real and is still a bug. Once it fails reliably enough to observe, change one thing at a time: tool description, policy line, few-shot example.

Step 5: diff against a good run

If the behaviour used to work, find a trace of the same golden case from the last good release and diff the node sequences, LLM call counts and token counts. A refactor that added a node, a catalog change that added three similar tools, or a model version change usually shows up immediately.

Common findings

SymptomUsual cause
Tool not calledTool missing from filtered catalog, or vague description
Wrong tool calledOverlapping descriptions between two capabilities
Planner loopsTool result not summarized into state, so the planner never sees it
Slow turnOne slow capability.invoke, not the LLM
Wrong entityResolver picked the first lookup result

Finish every investigation by adding the case to the golden suite, so the same bug cannot come back unnoticed.
