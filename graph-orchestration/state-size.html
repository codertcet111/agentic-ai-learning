Keeping GraphState small

Keep LangGraph state small by storing large tool results by reference, summarizing for the planner and measuring checkpoint size, so resumes stay fast and cheap.

2 min read

Graph state is convenient. Anything a node returns is available to every later node, survives pauses, and appears in debugging tools. That convenience is exactly why state tends to grow until it hurts.

Why size matters

  • Checkpoint writes. State is serialized after every step. A 300 KB search result held in state is written five or six times in one turn.
  • Resume latency. Loading and deserializing a large checkpoint adds latency to every form submission.
  • Prompt bloat. Nodes tend to pass "the state" to the LLM. Large state means large prompts and higher cost.
  • Trace exports. If state is attached to spans, it is uploaded too.

Store by reference

When a capability returns a large payload, write it to step_results and keep a reference and a summary in state:

result = await provider.invoke(cap, args, ctx)
sr_id = await step_results.insert(turn_id, cap.id, result.data)
summary = summarize_for_planner(cap, result.data)   # deterministic, small

return {
    "step_result_ids": [sr_id],
    "observations": [{"capability": cap.id, "summary": summary, "ref": sr_id}],
}

The summarizer is code, not an LLM: row counts, key fields of the first few rows, totals. The planner rarely needs all 200 rows to decide what to do next. Compose and presentation, which do need the rows, load them by id.

What belongs in state

KeepMove out
Ids: conversation, turn, pending interactionFull tool responses

Measure it

Add a cheap check after each node in development: serialize the state and log its size. Put a soft limit on it (say 32 KB) that logs a warning, and a test that fails if any golden case exceeds a hard limit. Size regressions are easy to fix the day they are introduced and tedious to track down later.

Reducers can grow forever

List fields with an append reducer, such as lookup_trace or observations, grow with every loop iteration. Cap them: keep the last N entries, or drop raw results once a summary exists. Per-turn thread ids (see checkpointing) also reset them naturally at the start of each turn.
