Multi-agent delegation

Structure multi-agent systems with a registry of agent cards, capability subsets per agent, a router that hands off ownership and one shared turn pipeline.

2 min read

A single agent with every tool works for a demo with ten capabilities. At sixty capabilities across HR, finance and IT, tool selection gets worse, prompts get long, and one team's prompt change breaks another team's flow. Splitting into several agents fixes this, as long as they share infrastructure instead of each becoming its own system.

Agent cards

Each agent is defined by data, not by a new graph:

{
  "id": "hr_assistant",
  "name": {"en": "HR Assistant", "ar": "مساعد الموارد البشرية"},
  "scope": "Leave, attendance, payslips and HR policies for the current employee.",
  "capabilities": ["leave.*", "attendance.read", "payslip.read", "knowledge.search:hr_policies"],
  "policy_module": "policies/hr.md",
  "voice": "friendly, concise, never speculative about pay",
  "handoff_to": ["it_helpdesk", "finance_assistant"]
}

Store cards in a JSON registry that is versioned with the code and loaded at startup. Validate on boot that every capability pattern matches something in the catalog.

One pipeline, many cards

All agents run through the same graph (load, plan, resolve, invoke, compose). What differs is the input to the planner: the capability subset, the policy text and the voice. This means fixes to turn admission, tracing or confirmation flows apply to every agent at once.

Routing between agents

The router picks the owning agent for a turn:

  1. If the conversation has an active agent and the message fits its scope, keep it.
  2. Otherwise classify the message against agent scopes, using a small, cheap model call with a typed output: {"agent_id": "...", "confidence": 0.0-1.0}.
  3. Below a confidence threshold, ask the user: "Is this about HR or IT?"

Record the active agent on the conversation so follow-up messages like "and next week?" stay with the same agent.

Handoffs

Sometimes an agent realises mid-turn that the request belongs elsewhere: the HR assistant is asked to reset a laptop password. It returns a plan of kind handoff with the target agent and a one-line summary. The graph sets next_agent_step, swaps the card and replans with the new agent's tools, all within the same turn and the same trace. The user sees one reply, not "please ask the other bot".

Limit handoffs to one or two per turn. Two agents passing a request back and forth is a loop with extra steps.

Supervisor or router?

Some frameworks favour a supervisor agent that calls worker agents as tools and combines their answers. That suits research-style tasks where several specialists contribute. For transactional assistants, where one domain owns each request, a router plus handoff is simpler, cheaper and easier to trace. Start with the router, and add a supervisor only when real tasks need several agents to collaborate on one answer.

Evaluating per agent

Tag golden cases with the expected agent. Track routing accuracy as its own metric. When a new agent is added, the routing cases for existing agents are the ones most likely to regress.
