Checkpointing and recovery

How LangGraph checkpoints work, how to persist them in MongoDB, how to resume after crashes or pauses, and how to keep checkpoint size and retention under control.

2 min read

A checkpoint is a snapshot of graph state saved after each step. Checkpoints are what let a workflow pause for a form and continue an hour later, survive a pod restart in the middle of a turn, and be inspected after the fact. They are also a place where data piles up quietly if you are not careful.

How it works

When you compile a graph with a checkpointer and invoke it with a thread_id, LangGraph saves the state's channel values after each super-step under that thread. Invoking again with the same thread_id continues from the latest checkpoint rather than starting fresh.

from langgraph.checkpoint.mongodb import MongoDBSaver   # or the async variant

checkpointer = MongoDBSaver(mongo_client, db_name="orchestrator")
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": turn_id}}
await graph.ainvoke(inputs, config)

Postgres, SQLite and Redis checkpointers exist too. Pick the store you already operate; checkpoint traffic is write-heavy but small.

Three uses

  1. Pause and resume. A node creates a pending form and the run ends. When the form is submitted, the service invokes the graph with the same thread id and the resume input. LangGraph's interrupt and Command(resume=…) APIs support this pattern directly.
  2. Crash recovery. If the process dies after invoke but before compose, a recovery job can resume from the last checkpoint instead of re-running the write.
  3. Inspection. graph.get_state(config) and get_state_history show exactly what the graph knew at each step, which is invaluable when a trace is not enough.

Choosing thread ids

Thread id defines checkpoint lineage. Two sensible choices:

  • Per turn (thread_id = turn_id): each turn starts clean, and conversation memory comes from the message store. Simple, small checkpoints, easy cleanup. This is the recommended default.
  • Per conversation: state accumulates across turns. Convenient for prototypes, but checkpoints grow with every turn and old state can leak into new turns.

For a form that spans turns, resume using the originating turn's thread id, which the pending interaction stores.

Keep checkpoints small

Every channel value is serialized on every step. A 200 KB tool result in state means 200 KB written several times per turn. Store large results in step_results and keep ids and summaries in state. See keeping GraphState small.

Never checkpoint secrets

Anything in state is persisted. Tokens and headers belong in run config (step 3), which is not saved. Add a test that serializes checkpoints and greps for a fake token.

Retention

Most checkpoints are useful for minutes, not months. Delete a turn's checkpoints when it completes successfully, keep failed ones for a few days for debugging, and keep paused ones until their pending interaction expires. A TTL index on a timestamp field, or a nightly cleanup job, keeps the collection from becoming your largest one by accident.
