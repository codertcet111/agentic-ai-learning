Bilingual compose for developers

Compose assistant replies in two languages such as English and Arabic: schema fields for each locale, consistent terminology, right-to-left rendering and locale-aware testing.

Shubham Mishra2 min read

Many products serve users in more than one language, and the assistant must reply in the user's language with the same accuracy in each. This article uses English and Arabic as the example pair, but the same approach applies to any combination.

Generate every language in one call

class ComposePayload(BaseModel):
    text_en: str = Field(description="Reply in English.")
    text_ar: str = Field(description="The same reply in Modern Standard Arabic.")
    follow_ups: list[FollowUp] = []

Requiring both fields in one schema keeps them aligned: the same facts, numbers and dates. A separate translation call adds latency and can drift. The client shows the user's locale and keeps the other as fallback, for example when the user switches language mid-conversation.

Respond in the user's language

Determine the locale from the request header or user profile, not from guessing the language of each message. Users often mix languages, typing an English product name in an Arabic sentence. Pass the locale into compose and mark it on each stored message.

Keep facts language-neutral

  • Pass numbers, dates and ids to compose as structured data, and format them per locale in code (digits, date formats, calendars) rather than asking the model to convert them.
  • Keep a glossary for domain terms such as leave types, statuses and product names, and include the relevant entries in the compose prompt so the same term is always used.
  • Never let the model translate proper nouns, codes or ids.

Right-to-left rendering

Arabic text needs dir="rtl" on its container. Mixed content (Arabic text containing English words or numbers) relies on the Unicode bidirectional algorithm, which usually works but can misplace punctuation at the edges of embedded English. Wrapping embedded left-to-right runs in <bdi> or using the dir="auto" attribute helps. Tables and cards should mirror column order. This is client work, but the server must mark locale and direction on every message.

Recipes and aliases

Known commands need aliases in every language (step 15), with normalization for each script, such as removing Arabic diacritics and unifying letter variants before matching.

Test in every language

Golden cases for each capability should exist in every supported language, with the locale header set. Check key facts in both text fields (the number 12 appears in both), and have a fluent speaker review a sample of real outputs regularly. Automated checks do not catch awkward phrasing.
