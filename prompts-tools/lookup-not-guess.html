Lookups: enrich, don't auto-select

Teach AI agents to look up entity ids instead of guessing: lookup tools, a lookup trace in state, replanning with candidates and asking the user when results are ambiguous.

2 min read

Language models are very good at producing plausible identifiers. emp_1042 looks like a real employee id whether or not it is one. Any agent that lets the model write ids directly will eventually act on an invented or wrong one. The fix is a firm habit: look up, don't guess.

The pattern

  1. A capability needs an entity id (employee, order, project).
  2. The planner calls a lookup capability with what the user said: a name, a description, a partial number.
  3. The full lookup result is appended to lookup_trace in state.
  4. The planner runs again with the candidates in view, and either picks the clear match or asks the user to choose.
  5. Validation checks that the chosen id appears in lookup_trace or an earlier tool result.

Policy wording

When a tool parameter is an id for a person, order or other record:
- Never write an id that you have not seen in a tool result in this turn.
- Call the matching search tool with the user's description.
- If exactly one result clearly matches, use its id.
- If several results could match, return need_input listing them.
- If none match, tell the user and ask for more detail.

Enforce it in code too

The policy makes the right behaviour likely. Validation makes the wrong behaviour impossible:

@field_validator("arguments")
def ids_must_be_seen(cls, args, info):
    seen = info.context["seen_ids"]          # from lookup_trace and step results
    for name, value in args.items():
        if name.endswith("_id") and value not in seen:
            raise ValueError(f"{name}={value} was not returned by any lookup")
    return args

A rejected id triggers the repair path, and the repair prompt explains which ids are valid.

Don't shortcut in the resolver

A common shortcut is to write resolver code that runs the lookup and takes the first result, "because there's usually only one". This hides ambiguity from both the model and the user, and fails silently in exactly the cases that matter: two people with the same name, two orders on the same day. Resolvers may run lookups. They must not choose.

Make choices pleasant

When the planner asks the user to choose, show a choice interaction with enough context to decide, such as name with department, or order number with date and total, not a bare list of ids. A good choice UI turns ambiguity into a single tap.
