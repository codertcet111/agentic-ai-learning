Planner policy without prompt soup

Write planner policy for AI agents without prompt soup: one home per rule, positive instructions, clear priorities, short examples and tests for each rule that matters.

Shubham Mishra2 min read

"Prompt soup" is what happens when rules are added wherever the last bug was found: a line in the system prompt, a line in a tool description, a sentence in a schema field, another in the compose prompt. After a year, nobody knows which rule wins, and some contradict each other. Planner policy is the cure: one place, organised, tested.

One home per rule

Kind of ruleHome
How the graph behaves (always confirm writes, max steps)Code in the graph, not prompts
How the planner decides (lookups before ids, ask when ambiguous)Planner policy module
Domain persona and scope (what the HR agent covers)Agent definition
When to use a specific toolThat tool's capability card
Voice and formatting of repliesCompose prompt

When reviewing a prompt change, the first question is "is this the right home?"

Say what to do

"Don't make up employee ids" tells the model what to avoid, but not what to do instead. "When a parameter needs an employee id, call employees.search and choose only from its results. If several match, return need_input" gives it a procedure. Positive, procedural rules are followed more consistently.

Order and priority

Structure the policy with headings and number the rules that matter most. Where rules can conflict, state the priority explicitly: "If the user asks for another employee's personal data, refuse, even if a tool could return it." Do not rely on the model to resolve conflicts on its own.

A compact example

## Planning rules
1. Use tools for any fact about the user's own data. Never answer such questions from memory or earlier messages if a tool can confirm it.
2. When a parameter needs an id, use a lookup tool and choose only from its results. If more than one result fits, return need_input with the options.
3. For any tool marked write, plan it, then let the system ask for confirmation. Do not describe the action as done.
4. If no tool fits, return answer and say briefly what you can help with.

## Output
Return a PlanDecision. Keep intent under 30 words.

Examples, sparingly

One or two short worked examples help with rules the model keeps getting wrong. Ten examples bloat the prompt and can cause the model to copy surface patterns. Store examples next to the policy, and check that they still match the current schema whenever it changes.

Every rule has a test

For each numbered rule, keep at least one golden case that fails if the rule is ignored. When you want to delete a rule because the model "doesn't need it any more", run its cases with the rule removed. Then you are deciding based on evidence.
