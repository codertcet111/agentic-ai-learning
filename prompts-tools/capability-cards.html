Writing capability cards for planners

Write capability cards (tool descriptions) that LLM planners follow reliably: clear identity, when and when not to use, parameter docs, side-effect class and examples.

Shubham Mishra2 min read

A capability card is everything the planner knows about a tool. The model cannot read your code or your API docs; it reads the card. Most wrong-tool bugs are card bugs.

Anatomy of a good card

id: leave.balance.read
summary: Get the current employee's remaining leave days by leave type.
use_when: The user asks how much leave they have, have left, or can take.
do_not_use_when: The user asks about leave policy rules in general
  (use knowledge.search) or about another employee's leave.
side_effect: read
parameters:
  leave_type:
    type: string, optional, enum [annual, sick, unpaid]
    description: Omit to return all types.
returns: List of {leave_type, remaining_days, as_of_date}.
  • summary: one sentence, starting with a verb, saying exactly what it does.
  • use_when / do_not_use_when: the most effective lines on the card. Negative guidance separates tools that would otherwise overlap.
  • parameter descriptions: formats, defaults and what happens when omitted.
  • side_effect: read, write or destructive. The graph uses this for confirmation rules, and the model uses it to be cautious.
  • returns: a brief shape, so the planner knows whether a follow-up call is needed.

Disambiguate siblings

Tools that sound alike are the main source of errors: orders.search versus orders.get, leave.balance.read versus knowledge.search. For each pair, make sure each card names the other in do_not_use_when. Then check with golden cases that use phrasings close to the boundary.

Keep the list short

Accuracy drops as the number of tools in the prompt grows, especially when many are similar. Rather than one agent with sixty tools, split by domain into sub-agents with a dozen each (see multi-agent delegation), and filter per user so that tools a user cannot use never appear.

Write for the model, not the API

Upstream catalog descriptions are often written for developers ("Returns LeaveBalanceDTO[] for principal"). Keep an orchestrator-side override for the summary and guidance fields, so you can tune wording for the planner without asking the API team to change their docs.

Test cards like code

Every card change can shift tool selection for other tools. Run the routing and tool-choice golden cases on any pull request that touches a card, and review the trace diff. Card edits are prompt edits.
