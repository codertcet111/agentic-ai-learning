Three-layer authorization

Apply three layers of authorization in AI agents: what the planner is shown, what the orchestrator allows at invoke time and what the upstream API finally enforces.

2 min read

In an agentic system, "can the user do this?" is checked in three places. Each layer has a different job, and none can replace the others.

Layer 1: what the planner sees

The capability list in the planner's prompt is filtered to what this user may use and what this agent covers. This is about quality and least surprise: the model does not suggest actions the user cannot take, and the prompt stays smaller. It is not a security boundary. A prompt can be manipulated, and the model can produce a capability id it was never shown.

Layer 2: what the orchestrator allows

At invoke time, the orchestrator checks, in code:

  • The capability id exists in the session's pinned catalog.
  • It is in the session's allowed capability list, derived from the user's roles at session creation.
  • It is within the current agent's scope.
  • If it is a write, explicit_action is set by the confirmation path.

This catches planner mistakes and manipulation before any request leaves the orchestrator.

Layer 3: what the upstream enforces

The domain API receives the user's own credential and applies its own authorization: role checks, ownership checks, record-level rules. This is the final authority. The orchestrator's checks reduce noise and risk; the upstream's checks are what actually protect the data.

Why all three

ScenarioCaught by
Model invents a capability id it was not shownLayer 2
Prompt injection asks for an admin-only toolLayer 2, and Layer 3 if it got through
User asks for another employee's payslip with a valid toolLayer 3 (record-level rule)
Role revoked after session startedLayer 3 immediately; Layer 2 on next session refresh
User sees a tool they cannot use and gets confusedLayer 1

Record which layer said no

When a call is blocked, record the layer and reason in trace metadata and the failure record: blocked_by: orchestrator, reason: not_in_session_capabilities, or blocked_by: upstream, status: 403. Support can then tell a user "your role doesn't include that" versus "that feature isn't available in the assistant yet". Patterns in these records also reveal drift between the catalog and upstream permissions.

Keep session permissions fresh

Layer 2 uses permissions captured when the session started. Keep sessions reasonably short, or refresh capability snapshots every few minutes from the domain, so a revoked role stops appearing in the planner quickly. Layer 3 covers the gap in the meantime.
