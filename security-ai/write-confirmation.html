Writes and explicit confirmation

Protect data-changing actions in AI assistants with explicit confirmation: graph-enforced confirmation steps, fingerprints, explicit action flags and operation ids against duplicates.

2 min read

An assistant that reads data can mislead. An assistant that writes data can do damage. Every write capability should require an explicit, informed confirmation from the user, enforced by code rather than requested in a prompt.

Four controls

  1. Catalog flag. Write capabilities declare requires_confirmation: true. Catalog validation fails if a write lacks it.
  2. Graph rule. The graph always routes such capabilities through a confirmation interaction before invoke. The planner cannot skip it, because it is an edge in the graph, not an instruction.
  3. Explicit action flag. The provider refuses to execute a write unless explicit_action=true, which only the confirmation-resume path sets.
  4. Operation id. Each confirmed write carries a server-generated id used as the upstream idempotency key, so retries and double-clicks execute once.

Informed confirmation

The confirmation must show what will actually happen, in plain language, with the resolved values:

Submit leave request?
  Type:      Annual leave
  Dates:     Thu 6 Nov – Fri 7 Nov 2026 (2 days)
  Approver:  Sara Lopez (Engineering)
  [Confirm]  [Edit]  [Cancel]

A fingerprint of these values travels with the confirmation. If anything changes before submission, the fingerprint no longer matches and the user must confirm again. What they confirm is exactly what runs.

Destructive actions

For cancellations, deletions and anything hard to reverse, add friction proportional to the risk: a distinct visual style, a clear statement that it cannot be undone and, for the most serious actions, typing a word or re-authenticating. Do not offer these actions at all through the assistant until there is a clear user need.

What the assistant says afterwards

Report only what the upstream confirmed: "Submitted. Request #5531 is pending approval." Never "Done!" before the response arrives, and never a success message when the upstream returned an error.

Tests

For each write capability: confirm executes once; cancel executes never; double confirm executes once; stale fingerprint is rejected; free text supersedes the confirmation with no write; and a prompt-injection attempt asking to "skip confirmation" still produces a confirmation. Tag these write and safety and require them to pass for every release.
