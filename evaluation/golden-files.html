Golden JSON cases

How to structure golden JSON test cases for an AI agent: one file per scenario, tags, fixtures, expectations that can be checked mechanically and schema validation in CI.

2 min read

Golden cases are the agent equivalent of regression tests: fixed inputs with expected behaviour, checked on every change. Step 20 explains why. This article covers how to organize the files so the suite stays useful as it grows to hundreds of cases.

Layout

evals/
  schema/golden_case.schema.json
  fixtures/
    principals.json          # fake users with roles and attributes
    upstream/                # recorded or hand-written API responses
  cases/
    leave/
      balance.basic.en.json
      balance.basic.ar.json
      request.ambiguous-approver.en.json
    safety/
      other-employee-salary.en.json
      injection-in-policy-doc.en.json
  baselines/
    2026-10-20/              # last approved real-model run

One file per scenario. Files are easy to review in pull requests, easy to delete, and merge conflicts are rare.

A case

{
  "id": "leave.request.ambiguous-approver.en",
  "description": "Two employees named Sara; the assistant must ask which one.",
  "tags": ["leave", "write", "multi-turn", "ambiguity", "en"],
  "principal": "employee_basic",
  "upstream": {"employees.search?q=Sara": "fixtures/upstream/two_saras.json"},
  "turns": [
    {"user": "book next Friday off, approver Sara",
     "expect": {"capabilities": ["employees.search"],
                "pending_interaction": {"kind": "choice", "options_count": 2},
                "no_capabilities": ["leave.request.create"]}},
    {"form_submission": {"approver_id": "emp_388"},
     "expect": {"pending_interaction": {"kind": "confirmation"}}},
    {"form_submission": {"action": "confirm"},
     "expect": {"capabilities": ["leave.request.create"],
                "upstream_calls": {"leave.request.create": 1}}}
  ]
}

Expectations that can be checked mechanically

Prefer expectations that a program can check exactly:

  • capabilities / no_capabilities: called or not called, optionally in order.
  • route: recipe, model, or a specific agent.
  • pending_interaction: kind and shape.
  • presentation_mode: table, card and so on.
  • upstream_calls: exact counts, which is critical for writes.
  • max_llm_calls, max_latency_ms: budgets.
  • response_contains_any: key facts, loosely matched.

Avoid exact text matches on model output. They break on every harmless wording change and teach the team to ignore failures.

Validate the cases themselves

A JSON Schema for golden cases catches typos such as "capabilites" before they produce a case that silently checks nothing. Validate every file in CI, before running anything.

Tags drive selection

pytest evals/ -m "safety or write"          # pull request gate
pytest evals/ --tags leave                   # working on the leave flows
pytest evals/ --live --tags all              # nightly with real models

Where cases come from

  • Every bug fix adds a case that failed before the fix.
  • Every new capability ships with at least one case per supported language.
  • Support tickets about confusing behaviour become cases once the desired behaviour is agreed.
