LLM-as-judge—with guardrails

Use LLM-as-judge evaluation for qualities like helpfulness and groundedness with clear rubrics and calibration, while keeping safety and tool correctness on deterministic checks.

2 min read

Some qualities of an answer cannot be checked with an exact assertion: is it clear, is it supported by the cited document, does it answer what was asked? An LLM acting as a judge, given a rubric, can score these at scale. Used well, it is a useful tool. Used for the wrong things, it gives false confidence.

What judges are good for

  • Groundedness: is every claim in the answer supported by the retrieved chunks?
  • Relevance: does the answer address the user's actual question?
  • Clarity and tone: is it concise, polite and in the right language?
  • Comparisons: is answer B better than answer A for the same input (pairwise)?

What judges must not decide

  • Safety allow or deny. Whether the assistant refused to reveal another employee's salary is a deterministic check on which capabilities were called and what the response contained.
  • Tool correctness. Whether the right capability was called with the right arguments is an exact comparison.
  • Write behaviour. Whether a confirmation was shown and exactly one record was created is counted, not judged.
If a wrong verdict would let a harmful behaviour ship, the check must be deterministic.

Writing a rubric

You are grading an HR assistant's answer.

Inputs: QUESTION, RETRIEVED_PASSAGES, ANSWER.

Score groundedness from 1 to 3:
3 = Every factual claim in ANSWER is directly supported by RETRIEVED_PASSAGES.
2 = Mostly supported; one minor claim lacks support but is not misleading.
1 = Contains a claim that is unsupported or contradicts the passages.

Return JSON: {"score": 1|2|3, "unsupported_claims": [string], "reasoning": string}

Use few, clearly defined levels. A 1–10 scale invites inconsistency, while three levels with written criteria give stable results. Ask for the reasoning and the specific unsupported claims. They make the score auditable and are often more useful than the number itself.

Calibrate against humans

Before trusting a judge, have two people score 50 or so answers with the same rubric, then compare with the judge's scores. Where they disagree, improve the rubric or the examples. Repeat this whenever you change the judge model. A judge that agrees with humans less often than humans agree with each other is not ready.

Known biases

  • Position bias in pairwise comparisons: run both orders and count only consistent wins.
  • Length bias: longer answers tend to score higher. Make conciseness part of the rubric.
  • Self-preference: a model may favour text written by itself. Prefer a different model family as judge when you can.

Use judge scores as trends

Track average judge scores per release and per tag, and investigate drops. Do not block releases on small movements in judge scores. Block on deterministic failures, and review judge regressions by hand.
