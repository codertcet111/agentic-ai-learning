Ship one copilot feature

A practical recipe for shipping your first AI copilot feature: one read-only capability, one agent card, stubbed CI, golden cases, a feature flag and a measured rollout.

2 min read

The fastest way to fail with an AI assistant is to try to launch it with forty capabilities at once. The fastest way to succeed is to ship one narrow, useful feature end to end, then widen it. This guide is that first slice.

Pick the slice

Good first features share three traits:

  • Read-only. Nothing can be broken by a wrong answer beyond a wrong answer.
  • Frequently asked. "How many leave days do I have?", "Where is my order?", "When is my next payslip?"
  • Backed by an existing API. You should not need a new endpoint.

The checklist

  1. Boundary note. One paragraph: which API, what auth, what the assistant must never do (step 1).
  2. Capability card. Id, one-line summary that says when to use it and when not to, parameter schema, side_effect: read.
  3. Agent card. A narrow persona with only this capability plus a fallback "I can't help with that yet" policy.
  4. Provider. Timeouts, typed errors, a span per call.
  5. Compose template. A presentation mode if a table or card fits, and fallback text in every supported language.
  6. Golden cases. Ten to twenty: common phrasings, each language, missing data, upstream error, an out-of-scope question.
  7. Stub LLM in CI. The whole flow runs without API keys on every pull request.
  8. Feature flag. On for the team, then a pilot group, then everyone.

Handle "not yet" gracefully

Users will immediately ask for things the slice does not do. The agent's policy should recognise out-of-scope requests and say plainly what it can do today, ideally with a quick-reply chip for the supported action. A clear "I can't book leave yet, but I can show your balance" builds more trust than an attempt at something unsupported.

Measure the pilot

  • Usage: turns per day and share that hit the capability.
  • Out-of-scope rate: what users asked for that you do not support. This is your roadmap.
  • Quality: thumbs up and down, and a weekly review of 20 random traces.
  • Cost and latency: tokens and p95 duration per turn.

Then widen

Add the next most-requested read capability, then the first write behind a confirmation (add a confirmed write). Each addition reuses everything the first slice built: admission, tracing, evals, flags. That reuse is what makes the second feature take days instead of weeks.
