Traces list: spot failures and slow turns

Use the Langfuse traces list to find failed and slow agent turns after a deploy: filter by environment and time, sort by latency and cost, and search by conversation or request id.

2 min read

The Tracing table is your shift dashboard. Filter by environment, time range and status before you open a single trace.

How to read this screen

  • Status / level: errors stand out from clean completions. Errors usually mean an upstream 4xx/5xx, a graph exception or a validation failure. Warnings often mean partial success or a failed automated check.
  • Latency column: sort descending to find the slowest turns after a deploy and compare them with your turn time budget.
  • Token and cost columns: when model prices are configured in Langfuse, cost is calculated per trace. Unusually expensive traces often reveal planner loops (many generations in one turn).
  • Search and filters: paste a conversation_id, request_id or trace id from your structured logs, or filter on tags and metadata.

A 15-minute post-release check

  1. Filter to the production environment and the last hour, or since the release time.
  2. Filter to errors. Group mentally by root cause: open three or four and see whether they fail in the same observation.
  3. Clear the error filter and sort by latency. Open the slowest three and check whether the time is in LLM generations or in tool calls.
  4. Sort by cost. Open the most expensive and count generations. More than your usual number points to replanning.

What the patterns usually mean

PatternUsual cause
Many errors in the planner observationCatalog or schema change, not the model
Many errors in capability.invokeUpstream outage, auth changes or circuit breaker open
Latency up, generation count unchangedProvider latency or a slow upstream API
Cost up, latency up, more generationsAmbiguous tools or missing lookup results causing replanning

Saved views

Save the filters you use every day, such as "production errors, last 24 hours" and "slowest turns this week", so the check takes one click. Combine this with alerts on error rate, so regressions surface before QA or users report them.
